# v42.21_3.21.2 多人价格预设重启显示修复

日期：2026-10-07。基线：已单人验收的42.21_3.21.1；目标游戏B42.21。当前源码为3.21.2，滚动ZIP保持3.21.1。用户授权修改后部署Workshop测试副本；不发布、不提交Git、不创建或替换备份。

## 反馈与核查结论

玩家称多人服务器重启后从预设1变成默认，未提供进一步日志或实际成交价格，因此无法认定实际价格丢失。

服务端实际购买/回收价覆盖、商城变体规则和转换配置保存在`GodSystem_CN_Data_MP_ItemConfig`世界ModData。Foundation.itemConfigStore调用migrate在原表上规范化，保留itemConfigPresets；applyRuntimeStores从该表恢复运行价格。默认只在明确执行itemConfigPresetApply(default)时写入空经济配置。跨存档文件`GodSystem_ItemConfigPresets.txt`是复用模板，Library.load不把模板重新写入当前经济配置。正常保存后重启不应重套旧模板，应用后做的单项修改也应保持。

实际服务器存储和命令安装器的Lua/Kahlua模拟证明：正常重启保持预设1、81购买价、11回收价与转换禁用；73是先前模板价格，重启没有把后续81修改覆盖回73。此证据不等于原生ModData磁盘保存或多人实机测试。

代码确认并复现的显示问题：

1. ensurePresets要求active槽位存在；Library.load用共享文件替换槽位后，文件为空/模板缺失会将active强制改成default，但81实际价格还在。因此“默认”选中不能证明价格已恢复。
2. MP初次打开无runtime.itemConfigPresets，applyPresets(nil)立即选中默认，再异步请求服务器状态，回复丢失或延迟时误导持续存在。
3. 既有断线/重连清理没有清除itemConfigPresets，可能暂时显示上一服务器或会话的选中状态。

## 最小修复

- ensurePresets只校验active是否为default或固定1/2/3，不再用模板是否存在决定当前配置身份。Library.load保留世界active；模板缺失仍不能读取，不从旧世界复活已删除模板。显式删除当前槽位/恢复默认的既有操作保留。
- UI区分未知状态与已返回默认状态。未收到预设列表时不标记任何槽位，禁用预设按钮并提示等待服务器；响应后恢复操作。不会把未知状态写成default缓存。
- Network.resetSessionRuntime清除预设缓存并将已打开窗口标为未知；关闭旧槽位、默认确认、备注弹窗，阻止旧回调在未知状态修改配置。
- 不改变购买/回收定价、倍率、经济版本、模板文件格式及世界存档键；不在重启自动applyPreset，也不试图从旧模板猜测恢复管理员的最新价格。
- CN/CH/EN与fallback增加等待状态提示，说明书说明世界配置与跨存档模板的区别。Workshop正文沿用用户测试副本，仅更新版本行。

旧版若已将active写成default，本次不根据价格相似程度猜测恢复预设，也不自动覆盖实际价格。若价格仍正确但需要恢复槽位标记，可覆盖保存当前配置到相应槽位；直接读取旧模板会替换之后的单项修改，必须由管理员自己决定。

没有增加监听、后台扫描或轮询；首次打开和用户手动重新打开等待中的窗口，复用既有预设请求。会话失效后保留的窗口可通过重新打开重试，避免缓存清除后一直没有新请求。
