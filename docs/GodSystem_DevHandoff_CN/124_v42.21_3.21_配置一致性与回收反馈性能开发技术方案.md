## 1. 版本与范围

版本结构按用户说明执行：

- `42.21`：目标游戏版本。
- `3`：系统级大版本，超大型变更时调整。
- `21`：基于现有功能的小模块或集中任务版本，本次目标为 `42.21_3.21`。
- 第三个 MOD 数字段用于专项小修，例如 `42.21_3.21.1`；本轮不预先增加 `.0`。

三项目标：

1. 核查全部现存沙盒配置是否真正影响对应业务，修复确认的问题，补齐单位、边界和生效时机。
2. 改善现有操作失败提示，重点贯通外部物品回收的真实原因；保留 console 诊断，不新建日志窗口。
3. 优化大批量回收的删除、核验、同步与批末更新；不改变价格、每日额度、来源权限和回收上架规则。

保留全部已开放的回收来源，包括地面散落物、世界容器、尸体、车辆、地上背包和嵌套容器。不得因没有多人实测而把已开放功能重新隐藏。本版不增加玩家必须安装的框架、后台轮询或新的回收数量限制。

## 3. 任务一：沙盒配置的业务一致性

### 3.1 建立 98 项审计矩阵

从唯一运行 schema `Contents/mods/GodSystem/42/media/sandbox-options.txt` 读取全部定义，在开发工具侧生成清单，人工补充业务证据。不要另手写一份 98 项运行配置表，使默认值产生第三个来源。

建议开发资料：`docs/开发技术支援/沙盒配置生效矩阵.md`；如需要生成器，放入 `tools/analysis/audit_sandbox_config.py`，复用现有本地化生成器的 schema 解析逻辑或保持相同解析规则。

### 3.3 修复方法

1. 保留 `RuntimeConfig.get()` 对 nil、false、0 的区别。禁止用会吞掉 false 的 `ok and value or fallback` 处理业务开关或权限。
2. 使用现有 `fromSandbox/readSandbox/applySnapshot` 入口，确认同一配置在 SP 与服务端得到相同有效值。只有发现字段校验遗漏时，才补该字段的有限数值、范围或整型处理。
3. 对必须为有限数值的配置拒绝 NaN/Infinity；禁止负价格或非数字直接进入结算。正常的合法沙盒值不受影响。管理员输入无效时不保存，并指出字段；不要以静默默认值伪装保存成功。
4. 配置冲突应有可读说明。例如装备成功率下限超过基础成功率，返回明确的相关字段；银行涨跌概率合计超过 100 时说明已有裁剪规则及最终有效概率，不把两个概率都无声显示为原输入。
5. 切换开关后同时验证 UI 隐藏和业务拒绝。后台效果下一次正常检查停止；不得只隐藏入口。培养、绑定、银行账本等已存数据不被开关清空，动态涨价仍保留原有关闭清层规则。
6. 价格相关变更沿用 `PricingRevision` 与 `EconomyPolicy.invalidate/rebuildConversionFloors`；装备沿用 `Equipment.config().token`；任务沿用 `taskGenerationToken`。只补缺失的关联，不新增全配置每帧比较。
7. 任务生成参数变更只按现有规则调整待接任务，已接任务不重复生成或重发奖励。初始配置不反向改变已发起始币。
8. 管理端、沙盒、UI 说明同步，CN/CH/EN 与 fallback 通过 YAML 生成。性能标签仍仅使用单个 `[性能]`，保留当前 7 页布局。

输入校验只作用于已有入口；不为了审计新增管理页面或全配置保存协议。缺少设置修改事件时，沿用现有读取时机，并如实标注“下一次操作/检查时生效”，不承诺未实现的即时广播。

### 3.4 大批量准备任务的稳定失效令牌

这是二次审查追加的必修项，属于本版配置一致性及回收稳定性范围。

已验证路径：`Prep.start()` 保存 `RuntimeConfig.Current` → `isCurrent()` 调用 runtime `getData()` → SP 再执行 `readSandbox()` 生成同值新表 → 下一步比较表引用失败。使用当前真实 `RuntimeConfig` 与 `RecyclePreparation` 模块、仅模拟 player/getData 外部边界的 Lua 5.1 探针复现：设置未变，任务仍成为 `failed/changed`。这不是新的实机日志结论。

修改方法：

- 不使用 `RuntimeConfig.Current`、`ItemConfig.Current` 或普通 state/data 表的引用作为业务变更标志。
- 增加小型共享函数 `RuntimeConfig.recyclePreparationToken(mode)`，返回固定字段构成的确定性令牌；不遍历 98 项、不扫描背包、不写存档。相关字段包括回收/商城/上架开关、价格版本、回收倍率、上架费比例与最低费、安全余量，以及按消费者补齐的商品可售规则。费用比例等未进入 `PricingRevision` 的字段必须单独列入令牌。
- 准备任务同时记录物品经济配置 `economyRevision`、有上架判断时的 `shopCatalogRevision`、范围筛选模式的现有 profile token，以及玩家/会话代次。目录 revision 不影响纯回收时，不为了无关目录变化取消该任务。
- `Prep.clear()` 在现有断线/主菜单清理中递增本地 session generation；任务携带代次，过期任务不能提交。保留玩家身份及存活检查。
- 普通钱包、历史记录或其他无关 MP 状态同步可以替换展示数据表；相关业务版本没变时不取消准备任务。分析缓存依赖相关版本；真正价格、资格、目录、筛选、功能开关变化时取消并提示对应原因。
- 物品 ID、来源、内容签名的逐项核验继续保留，令牌只证明配置没有变化，不证明物品没有变化。
- `getData()` 可能刷新配置，先取得当前数据及配置，再比较业务令牌，避免检查后读取才改变状态。

回归必须覆盖：SP 重复调用 `getData/readSandbox` 但值不变；MP 无关 state 更换表但业务版本相同；上架费、功能开关、相关价格/目录/profile 真变更；断线与新会话。大于 200 件的准备、确认、提交必须完整走通，不能只测试函数返回一个 job。

### 3.5 配置测试的最低有效标准

仅验证 `RuntimeConfig.get(key) == value` 不算业务生效测试。每项至少有一条 A/B 业务断言，例如：

- 刷新费设为 0 时刷新不扣币，设为 7 时扣 7；不能只检查标签。
- 回收倍率 0 与 2 得到对应实际回收结果，购买倍率不越过已明确的管理员定价优先级。
- `EnableRecycleListing=false` 隐藏上架入口，旧客户端直接发上架请求也被拒绝。
- 任务容量按基础值和购买 bonus 计算；不同设置不得被旧的绝对容量覆盖。
- 每币经验设置 1/25 时，按实际兑换调用检查参数和结算结果。
- 水价 0、电价 0 时仍供给但不扣费；停机、子开关和已有预留水退款符合现有规则。

对原生供电、攻击、反作弊等无法自动证明的效果，记录“读取与分支已验证，实际游戏行为待测”；不得声称 98 项全都经过实机测试。

## 4. 任务二：失败原因贯通与玩家提示

### 4.1 沿用现有结果协议

继续使用 `Protocol.S2C.Result` 的 `ok/code/args/operationId/data`。客户端将 `code/args` 本地化，服务端不发送新中文句子。新增字段仅为短小、可选的上下文；不发送完整物品列表、原生对象或整个异常堆栈。

可增加共享模块 `GodSystem_RecycleResult.lua`，只做固定原因码到结果码/文案的映射及简短上下文规范化。SP/MP 使用同一映射；不建立覆盖所有交易的新框架。

现有 `GodSystem_Result.lua` 继续负责 success/failure 结果结构；新模块只包含回收原因的业务映射，不复制结果构造器。

拟新增内部接口（属于本版待实现接口，不是现有游戏 API）：

```lua
-- 失败时附带原因；成功时仍返回原来的 row，兼容旧调用方。
GodSystemExternalRecycle.resolve(player, descriptor, cache)
-- -> row | nil, reason, detail | nil

-- 成功仍以第一个 boolean 为准；第二、三项只补失败原因。
GodSystemExternalRecycle.remove(row, batchContext)
-- -> boolean, reason | nil, detail | nil

GodSystemRecycleResult.fromReason(reason, detail, recovery)
-- -> code, codeArgs, compactContext
```

`batchContext` 为可选参数，未传时保留现有单件移除/同步行为。新模块必须接入现有启动 require 路径，并通过本地 require 和协议检查。

### 4.2 原因拆分与示例

以下是建议稳定内部原因及对应提示语义，最终键名统一以 `Recycle...` 开头；原有通用码保留兼容。

| 原因 | 权威依据 | 玩家提示 |
|---|---|---|
| `distance` | 玩家所在格、目标格或楼层不符合已有规则 | 距离过远或楼层不同，请靠近后重新选择 |
| `unloaded` | 当前地块不可读取 | 目标所在区域暂未加载，请稍后重新选择 |
| `blocked` | 原生 `isBlockedTo` 拒绝通行 | 目标被墙或障碍阻隔 |
| `protected` | 原生安全屋权限检查拒绝 | 无权回收该区域物品；不泄露安全屋成员资料 |
| `locked` | 原生容器锁/车辆访问接口拒绝 | 容器上锁或无法访问 |
| `removeDenied` | 原生 `isRemoveItemAllowed(item)` 返回 false | 该容器不允许移除所选物品 |
| `changed` | 身份、来源或容器路径不再匹配 | 物品已移动或不存在，请重新选择；不得断言是其他玩家拿走 |
| `contentsChanged` | 容器内容签名与确认不一致 | 容器内容已变化，请重新确认，避免误删内部物品 |
| `disabled` | 功能总/子开关关闭 | 此功能已关闭 |
| `nativeReadFailed` | 必要原生读取或成员访问抛错/无效 | 无法核验物品或容器，本次操作取消；带短操作编号用于查日志 |
| `removeFailed` | 删除后仍存在或删除异常 | 根据恢复结果区分已恢复与待核对 |
| `currencyFailed` | 奖励发放失败 | 发放失败；仅恢复已核实时显示物品已恢复 |
| `configInvalid` | 关联配置不合法 | 显示相关字段和修正方向 |

补充关联情形：余额不足、旧商城报价、处理中、客户端未收到结果、回滚不完整。保留这些模块已有细分码，修正被 `legacyResultCode` 或泛化文本吞掉的已确认分支；不大规模替换全部历史返回格式。

### 4.3 区分取消、恢复与不确定

1. **变更前拒绝**：明确操作已取消，没有由本次操作删除物品或扣费；可以重新选择。
2. **变更后失败、完整恢复**：必须根据恢复返回值和物品身份验证，才显示“操作失败，物品已恢复”。非空容器、装备穿戴/手持状态也纳入现有恢复核验。
3. **恢复未完成或已发款但结果不明**：保留 `TransactionOperationUnknown` 等现有保护，不伪装成功/失败，不解除账号保护，不建议玩家重新付款。
4. **客户端发送失败/超时**：提示“未收到结果，可能仍在处理”，不宣称未执行。沿用当前超时请求指纹和 60 秒内的 `opId` 复用；该重试窗口内不得把原交易作为新操作重发。超过窗口或重连后无法关联原操作时，不能提示“安全重试”，应先核对已有结果；本版不新增自动重发，不把长期相同业务意图全部去重。不延长所有命令超时来掩盖服务器停顿。
5. **提交后仅通知失败**：权威结果已成功则保留成功回执；不能因为 `sendServerCommand` 抛错而发退款或恢复已兑换物品。在受影响回收分支中将提交前业务异常和提交后通知异常分开处理。

### 4.4 调用路径改动

**SP**：`ClientRuntime_Recycle.recycleSelectedItems()` → `ExternalRecycle.resolve/remove()` → 共享原因映射 → runtime `text/notify()`。`RecyclePreparation` 在点击后分析、确认或取消时采用同一原因语义。保留 SP 现有业务入口，不为了本版把全部 SP 交易改造成服务端回执系统。

**MP**：`Network.send()` → `Commands.recycle/recycleSelectedInternal()` → `ExternalRecycle` → `complete()/finishCode()` → `TransactionOps.remember()` 保存结果码和简短上下文 → `Network.OnServerCommand()` 本地化显示。重发仍得到原结果及原原因，不重新扫描或执行删除。

正常拒绝返回码，不调用 `error()` 制造红色错误。原生抛错需记录必要阶段，不能只在外层捕获后失去具体来源。

准备阶段当前在 `verifyEntry/processEntry/finishPass/step` 对正常物品/状态变化使用 assert，再把异常统一改为 changed。将这些预期拒绝改为 `ok, reason` 返回并传入 `Prep.cancel()`，分别保留物品变动、配置变动、内容变动、余额/资格变动和读取异常。assert 仅用于真正的内部不变量，不靠 catch 后改提示来消除 Kahlua 红错。

### 4.5 console 诊断

沿用 `GodSystemDiagnostics.issue(side, feature, phase, code, opId)`，内容只含版本、运行端、功能、阶段、原因和操作编号。

当前去重键有 opId 时只按操作去重，可能把后续更重要的恢复失败日志压掉。本版只调整受影响诊断：

- 同一操作、同一阶段和代码的重试只记录一次。
- 后续进入恢复失败或状态不明时仍可记录一条，不被先前普通拒绝压掉。
- 仍保留 128 项有界记录；没有 opId 的重复异常沿用 30 秒合并。
- 正常距离/锁定拒绝不逐件打印；一次请求最多给出一条主要业务原因。
- 不输出完整请求、ID 清单、账户秘密或其他 MOD 日志，不新增日志文件。

## 5. 任务三：大批量回收末段优化

### 5.1 先记录分阶段基线

以当前 3.20.3 原样跑基线，再进行修改。测量范围：

- 地面同格 100/500/2000/5000 件；分布多格的同量样本。
- 人物背包、世界容器、尸体、车辆、嵌套背包分别测试；包含混合来源。
- 记录选中分析、索引建立、权限/内容预检、删除前复核、原生删除、删除后核验、同步调用、发款、UI/重量更新、失败恢复。
- 统计世界列表 `get()` 次数、成员检查次数、完整背包扫描次数、同步函数调用次数、受影响容器/车辆部件数。
- 默认不输出性能日志；仅开发诊断开启时按请求汇总。Lua 模拟成本与游戏原生成本分栏，网络调用数不冒充真实包数。

不得沿用 3.20 的“定位阶段”模拟结果，作为本轮整笔交易或游戏帧率提升的证据。

### 5.2 地面成员检查

替换 `ExternalRecycle.inWorld()` 的逐项 Lua 循环：

```lua
-- 具体取值经现有 B42JavaCalls 受保护调用完成。
local objects = square:getWorldObjects()
local present = objects:contains(worldObject)
```

要求：

- 读取失败返回失败，`false` 必须作为真实“不存在”保留，不能回退允许。
- 保留物品与世界对象双向身份、当前位置、同楼层、距离和权限检查。
- 删除后继续检查原世界对象确实不在该格列表中，不能只检查 `item:getWorldItem() == nil`。
- `contains` 已在调用桥注册；测试 Java 列表对象、返回 false 和抛错边界。不要为了测试通过仅给 Lua fixture 添一个永远 true 的 contains。
- 原生 `contains` 内部仍为线性查找，原生列表删除也可能是线性；成果是减少 Lua→Java 的逐元素调用，不宣称整个交易变为严格 O(n)。

保留 3.20 的单请求地块 ID 索引与重复 ID 拒绝，不改成跨请求持有世界对象。

### 5.3 事务内批次上下文

只为当前已存在的同步回收请求建立临时 `batchContext`，建议结构：

```lua
{
    removed = {},                 -- 当前操作恢复账本，保留真实 item/source/equipment
    containers = {},              -- 以真实 ItemContainer 为键的已删除列表
    dirtyContainers = {},         -- 界面脏标记合并
    vehicleParts = {},            -- 重量更新去重
    syncAttempted = {},           -- 已尝试发送的分组，用于失败补偿
}
```

- 生命周期只覆盖一次调用；完成、拒绝、恢复或异常后释放，不写入存档或跨会话复用。
- 不修改 item ID、源描述格式、双哈希指纹、账户回执 64 条上限、现有每日额度或上架规则。
- 单件旧调用未提供 `batchContext` 时照旧立即同步和更新，避免影响其他使用者。
- 现有服务端 `removeItemFromContainer()` 还被其他交易使用；只能增加显式可选上下文或回收专用适配，不直接全局改变其同步时机。

### 5.4 容器同步合并

1. 删除仍逐件按确切物品执行，并保留装备移除钩子、穿戴/手持解绑和删除结果核验。
2. 当前回收请求内，已核实删除的物品按真实容器收集。
3. 使用 `ArrayList.new()` 和 `:add(item)` 建立独立 Java 列表，不使用 Lua table，不使用仍在变化的原容器列表。
4. 服务端调用 `sendRemoveItemsFromContainer(container, javaItems)`，每次最多 200 项，避免 20000 项形成一个超大同步调用。这个上限只限制内部消息分块，不限制玩家本次回收数量。
5. 原生函数返回 void。成功标准是调用完成，不能要求返回 true；真实送达由游戏网络机制处理，自动测试只能证明参数/调用路径。
6. 普通地面散落物继续使用 `square:transmitRemoveItemFromSquare(worldObject)`，不混入容器批量接口，不伪造 floor 容器。
7. 直接来源恢复仍按已有 `restore()` 使用原生物品放回与补偿同步。不能用新创建的同类型物品替换原物品，导致身份、内容、培养或耐久丢失。

本地已找到原版接口，实施时验证实际暴露及来源路由。若批量接口在某个原生来源不能安全使用，则该来源继续原单件同步，不关闭其直接回收；记录实际采用路径。不要尝试新的私有网络包替代接口。

### 5.5 失败、补偿和提交顺序

遵循现有请求内结算边界：

```text
请求/指纹/权限检查
→ 记录 processing
→ 预检并建立临时索引
→ 逐件复核、解绑、记录恢复账本、删除并核验
→ 合并原生删除同步与受影响容器/车辆更新
→ 按原规则发款、额度及业务数据结算
→ 保存 done 回执
→ 发送结果和必要状态
```

具体要求：

- 可能部分修改的当前物品必须进入恢复跟踪，即使其删除调用最终抛错；不能漏掉“调用失败但实际已删”的物品。
- 预检通过不是删除授权的永久缓存，执行前仍核对真实来源、可访问状态和物品身份。
- 批量同步若抛错，按当前提交前失败路径恢复已删物品；已有删除通知可能部分送达，恢复必须有相应原生添加/世界对象补偿同步。
- 已发送分组不可假定“没有生效”；补偿覆盖所有真实修改，不依赖 pcall 判断远端是否收到。
- 恢复未核实时使用 unknown，不发款，不提示已恢复。按已有发款辅助的部分失败恢复规则处理，不新增双倍补偿。
- `done` 成功后发结果/状态失败只做诊断，保留回执以便同 opId 查询；不得由外层异常处理重新恢复物品。
- 服务端回收的 `complete()` 在 `remember()` 后设置明确的 `receiptCommitted` 标志；外层 pcall 出错先判断是否已提交，再决定能否恢复。特别覆盖 payout 为 0 时提交后通知失败，不能因为 `payoutAttempted == false` 把已提交物品恢复、回执覆写为失败。
- `storeCheckpoint()` 不是立即落盘。这一版保持原 ModData 保存机制，不保证游戏进程崩溃时物品与账本的跨存储原子性，不用措辞掩盖这个边界。

SP 与 MP 使用同一外部定位、原因映射和批末更新语义；MP 才进行原生网络合并。SP 继续当前本地结算，不引入伪网络或新的持久化回执层。

### 5.6 车辆与展示更新

- 每个受影响车辆部件在当前批次结束后执行一次 `part:setContainerContentAmount(container:getCapacityWeight())`，异常恢复后重新更新。
- `setDrawDirty`、库存 dirty 和 UI 刷新按真实容器/玩家合并；不得略过需要更新的嵌套容器和车辆。
- 一次成功请求沿用一次结果/状态发送，不为每件物品再发送 GodSystem 完整状态。
- 不减少逐件必要身份和删除核验，不使用 `container:clear()`、`RemoveAll(fullType)` 代替选中 ID 删除，以免删掉未选物品。

### 5.7 本版不做跨帧破坏性交易

现有 `RecyclePreparation` 的非破坏性准备已支持大批量分帧；范围回收也有独立的批次与取消模型，本版保留。

普通选中回收的删除、发款、回执仍在一次权威调用内完成。理由是跨帧后需要新增物品占用、防并发、存档中断恢复和客户端状态协议；不能只把 for 循环搬到 OnTick。

本版先减少重复成员遍历、同步调用和重量/UI 更新。如果测量发现原生删除仍占主导，报告残余成本，供下一版单独决定是否实现带恢复日志的异步交易。不得为显示“性能优化”而新增无依据框架、强制小批量或提高已有限制。
