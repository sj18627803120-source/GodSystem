## 已知问题与根因

- 当前 `GodSystem_ConversionRelationsUI.lua` 是固定坐标的独立窗口，虽已改为按终端字体重排并置顶，但用户仍反馈“增删改查无用”。不要继续修补固定坐标布局，应按上述交互重构。
- 当前右侧直接编辑 `Base.*` 字符串和逗号分隔的 `fullType:count`，可读性差，也没有真实物品选择验证。
- 当前列表第二行显示内部 ID 与配方名。用户明确不需要该层技术信息。
- 现有 `localSave()`（SP）和 `Commands.itemConfigRelationSet/Delete`（MP）可以作为最终保存通道，但客户端 UI 需要在发送前完成搜索选择与数据组装。服务端仍必须重新 `sanitize`、拒绝循环、拒绝不存在物品和并发版本冲突。

## 建议实现路径

1. 先审查 `GodSystem_ItemCatalog` 和 `GodSystemItemConfigService`：复用其分批目录、250ms 搜索与稳定 `fullType` 选择能力，避免在绘制中创建物品或全量扫描。
2. 将转换关系 UI 改为模型驱动：`selectedId`、`editingNew`、`sourceSelection`、`outputRows`。绘制仅读当前模型。
3. 左侧使用滚动列表，单独在列表上方保留“新增关系”按钮；每行使用 `runtime.getItemDisplayName(fullType)`，摘要格式为 `来源 → 数量 产物`。
4. 右侧对来源与每个产物提供搜索输入、最多 20 条候选和明确的选中态。搜索防抖 250ms；候选只在输入变化时重建。候选列表必须显示中文名与较小的 `fullType` 辅助文字。
5. 对一对多关系采用可扩展的“产物行”模型。内置 `candy_package` 等关系有多个输出，不能因界面简化而丢失。每行包含物品选择、数量和删除；提供“添加产物”。
6. 保存前转换为现有协议结构 `{ sourceFullType, sourceCount, outputs={{fullType,count},...}, note, enabled=true }`；内置 ID 与自定义 ID 的现有语义保持不变。
7. SP 调用本地保存；MP 只发送 C2S 命令，等待服务端 `ItemConfigRelations` 回传刷新。不可依赖客户端提交的显示名称或物品存在性。
8. 延续主界面主题、`GodSystemUISafety.installList`、私有按钮颜色副本和 `GodSystemUI.presentOverlay`。UI 尺寸与行高应从实际字体高度计算。
