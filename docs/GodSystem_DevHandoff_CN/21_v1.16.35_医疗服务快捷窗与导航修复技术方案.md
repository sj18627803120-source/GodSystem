## 功能设计

### 升级页医疗服务

医疗服务作为升级页中的新行展示，不新开左侧大页签，避免左侧导航继续膨胀。

建议新增四个服务行：

| 服务 | 价格 | 作用 |
| --- | ---: | --- |
| 检查病毒感染 | 50 | 检查玩家是否有僵尸病毒感染，只反馈结果，不治疗 |
| 压制感染 | 1000 | 若已感染，延长尸变前时间，默认延长 24 游戏小时 |
| 治疗伤势 | 5000 | 清除身体伤势、普通伤口感染和负面伤害，恢复生命，不清除僵尸病毒 |
| 清除病毒 | 10000 | 清除僵尸病毒感染状态，不负责恢复所有伤势 |

所有服务都必须弹窗确认。执行后必须有明确反馈：

- 成功扣费并执行：提示服务名称、花费、关键结果。
- 系统币不足：不执行，不扣费。
- 不需要执行：例如未感染时压制/清除病毒，不扣费，并提示未检测到病毒。
- 接口异常：不扣费或回滚扣费，并提示操作失败。

为了避免“清除病毒”变成免费检查，确认弹窗文案要明确：

- 点击清除病毒后会先检查病毒状态。
- 如果未感染，不扣费并提示不需要清除。
- 如果已感染，扣除 10000 并清理病毒。

这样优先避免误扣高额系统币。`检查病毒感染 50` 的价值是低成本主动确认状态，而不是强制隐藏其他按钮的状态判断。

### 医疗状态判定

建议新增共享/双端一致的医疗工具逻辑。因为 PZ Lua shared 文件加载环境复杂，最稳方案是：

- 在客户端 `GodSystem_Core.lua` 中增加单人使用的本地 helper。
- 在服务端 `GodSystem_Server.lua` 中镜像同名核心逻辑，供多人服务端执行。
- 后续如果代码明显重复，再抽到 shared 文件；本版优先稳定，避免 shared 在 client/server 访问环境差异下引入红字。

建议接口形态：

```lua
GodSystem.getMedicalStatus(player)
```

返回：

```lua
{
    hasBody = true,
    infected = true or false,
    fakeInfected = true or false,
    infectionLevel = number or nil,
    infectionTime = number or nil,
    canCure = true or false,
    hasInjury = true or false,
}
```

多人服务端对应本地函数：

```lua
local function medicalStatus(player)
```

检测病毒时优先读：

- `body:isInfected()` 或 `body:IsInfected()`，按实际 B42 暴露情况使用 `pcall` 包裹。
- `body:IsFakeInfected()` 或类似 getter，如果存在就读取。
- `body:getInfectionLevel()` / `body:getInfectionTime()` 如果存在，作为反馈补充，不作为唯一判断。

检测伤势时遍历 `body:getBodyParts()`，存在以下任一情况视为有伤：

- 部位生命不满。
- 出血、深伤、骨折、划伤、割伤、咬伤、烧伤。
- 普通伤口感染 `isInfectedWound()`。
- 全身生命 `body:getHealth()` 或 `body:getOverallBodyHealth()` 低于满值。

### 清除病毒

清除病毒只处理全局僵尸病毒状态，不强制修复所有伤口。执行顺序：

1. 获取 `player:getBodyDamage()`。
2. 判断是否感染。
3. 已感染时扣费。
4. 依次尝试：
   - `body:setInfected(false)`
   - `body:setIsFakeInfected(false)`
   - `body:setInfectionTime(-1.0)`
   - `body:setInfectionMortalityDuration(-1.0)`
   - `body:setInfectionLevel(0)`
5. 再次读取状态，作为结果反馈。
6. 写历史记录。

每个 setter 都用 `pcall` 包裹。只要核心 `setInfected(false)` 成功，就可以认为清除主路径成功；其他 setter 是防残留兜底。

### 压制感染

用户已确认选方案 A：延长尸变前时间。

默认设计：

- 价格：1000。
- 每次压制：延长 24 游戏小时。
- 可重复购买。
- 未感染时不扣费。

推荐实现策略：

1. 先确认 `body` 已感染。
2. 扣费。
3. 优先尝试读取 `body:getInfectionTime()`，如果存在，则执行：

```lua
body:setInfectionTime(math.max(0, currentInfectionTime - 24))
```

这里的思路是把感染进程往回拨 24 小时。

4. 如果存在可读的死亡/转化时长 getter，再尝试把对应 duration 增加 24 小时。
5. 如果 getter 不存在，不要盲目覆盖 `setInfectionMortalityDuration()`，避免把沙盒/服务器原本的感染时长改成错误固定值。
6. 如果 `getInfectionTime()` 不存在，则退化为降低 `infectionLevel`，并在反馈中提示“已尝试压制，具体剩余时间取决于游戏内部状态”。

注意：`getReduceInfectionPower()` 在官方健康面板里只看到 getter，当前没有在 Lua 文件中发现稳定 setter，因此本版不把“抗生素强度”作为主实现。

### 治疗伤势

治疗伤势是身体治疗，不清除僵尸病毒。

价格：5000。

执行内容：

- `player:setHealth(1.0)`，如果方法存在。
- `body:RestoreToFullHealth()`，如果方法存在。
- `body:setOverallBodyHealth(100)`，如果方法存在。
- 遍历 `body:getBodyParts()`，对每个部位尽量执行：
  - `part:RestoreToFullHealth()`
  - `part:setBleedingTime(0)`
  - `part:setDeepWoundTime(0)`
  - `part:setDeepWounded(false)`
  - `part:setFractureTime(0)`
  - `part:setScratchTime(0)`
  - `part:setScratched(false, true)`
  - `part:setBurnTime(0)`
  - `part:setCutTime(0)`
  - `part:setCut(false)`
  - `part:setBiteTime(0)`
  - `part:setAdditionalPain(0)`
  - `part:setWoundInfectionLevel(0)`
  - 如果有 stiffness，并且玩家 fitness 可用，则同步移除 stiffness。

治疗前若检测不到伤势，可以不扣费并提示“当前没有需要治疗的伤势”。如果用户希望治疗也可作为满血保险服务，可在后续改为强制收费执行。

### 检查感染

价格：50。

执行逻辑：

1. 弹窗确认。
2. 扣费。
3. 读取感染状态。
4. 反馈：
   - 未感染：未检测到僵尸病毒。
   - 已感染：检测到僵尸病毒，建议使用压制感染或清除病毒。
   - 无法读取：检查失败，不扣费或回滚扣费。

检查结果不写入永久状态，只写历史记录，避免不同角色死亡/重生后残留错误状态。

## 单人和多人数据流

### 单人

客户端直接执行：

```text
升级页选择服务 -> 确认弹窗 -> GodSystem.performMedicalService(action)
-> canAfford -> addPoints(-cost) -> apply medical effect -> history + notify -> save -> UI refresh
```

所有实际改角色身体状态的代码都放在 `GodSystem_Core.lua`，不依赖服务器。

### 多人

多人必须走服务端：

```text
升级页选择服务 -> 确认弹窗 -> GodSystemNetwork.send("medicalService", { action = ... })
-> server Commands.medicalService -> canAfford -> addPoints(-cost) -> apply to player body
-> finish(player, true/false, message, payload) -> client result/state -> notify + refresh
```

建议同时做一个幂等的客户端镜像应用：

- 服务端成功后回包 `{ kind = "medicalService", action = "...", applied = true }`。
- 客户端收到成功 result 后，可以对本地角色重复执行对应的状态清理，作为 MP 同步延迟兜底。
- 这些操作本身是幂等的，例如 `setInfected(false)`、`setBleedingTime(0)`，重复执行不会造成额外收益。

多人不做强反作弊。服务端负责扣费和执行，客户端只负责确认、显示和成功后的本地兜底。

## 左侧导航越界修复

### 当前问题判断

左侧导航现在是自绘面板 + 一组 `ISButton` 子控件。当前逻辑通过 `updateNavButtonVisibility()` 判断按钮是否和视口相交：

```lua
button:setVisible(y + h > top and y < bottom)
```

这个条件允许按钮只有一部分在视口内时仍然显示。由于这些按钮不是放在真正裁剪容器中，底部半截按钮会画出导航框，表现为“下面的按钮超出 UI 框”。

### 修复策略

优先做小改动，不引入新容器：

- 只显示完整落在导航视口内的普通导航按钮。
- 计算视口时留出上下内边距，避免贴边。
- 滚轮仍按整行高度滚动。
- 如果最大滚动值导致最后一行出现半截，则把滚动值吸附到行高步进，或在 `getNavScrollMax()` 中按行高取整。

建议实现：

```lua
local visible = y >= top and (y + h) <= bottom
button:setVisible(visible)
```

如果这会导致最后一项无法出现，再调整 `getNavScrollMax()`：

```lua
local step = itemH + gap
return math.max(0, math.ceil(rawMax / step) * step)
```

不建议本版做复杂 stencil 裁剪，因为 `ISButton` 子控件裁剪在 PZ UI 里更容易引入点击和渲染边界问题。

## 风险和边界

- 压制感染的内部 API 不如清除病毒明确。当前没有找到稳定的 `setReduceInfectionPower` Lua 调用，因此本版优先通过回拨 `infectionTime` 实现。必须用真实感染角色测试。
- 治疗伤势和清除病毒必须保持分离。治疗伤势不清除僵尸病毒，否则 10000 的清除病毒功能失去意义。
- 多人服务端改身体状态可能存在同步延迟，因此允许成功回包后客户端幂等兜底执行一次。
- 快捷窗本版不做自定义按钮，只做固定按钮和数据结构预留。
- 左侧导航修复只做完整可见行，不做复杂裁剪容器，降低 UI 红字风险。
