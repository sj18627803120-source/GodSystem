# v1.16.63 终端即时同步与车辆模块消耗修复

## 实测问题

- 多人服务端已经完成终端容量、减重或空间减载升级，但客户端当前持有的终端实例仍显示旧值；丢到地上再拾取或重登后才刷新。
- 部分 MOD 车辆调用 `vehicle:repair()` 后已经修复大部分损坏，但仍残留无法创建的无效缺失部件。旧逻辑把“仍有任一损坏”判为完全失败，返还修复模块，造成有时消耗、有时不消耗。

## 终端即时同步

- 服务端按真实终端实例生成 `terminalSync`，包含 `itemId`、外层/内层容量、外层/内层减重、减载等级和减载值。
- 领取、容量升级、减重升级和空间减载升级成功后，现有结构化结果立即附带权威状态。
- 打开终端升级页面时复用 `syncClientData` 请求一次服务端状态；不在列表绘制、普通刷新或逐帧事件中发送。
- 服务端对变化实例调用 `syncItemFields()`，客户端再按真实 `itemId` 修正当前已存在的终端对象，避免按类型误更新其他物品。
- 客户端普通终端查找继续只读。只有收到服务端明确 payload 时才写入显示实例；穿脱或库存转移期间延迟一次应用，找不到 ID 时只保留短时待处理状态。

## 车辆模块消耗

- B42.19 的 `vehicle:repair()` 可能在无法创建某个 MOD 部件时留下 `Couldn't find item nil2`，但其他标准损坏已经实际修复。
- 修复结果改为比较修复前后的损坏数量：
  - `after.damaged < before.damaged`：存在真实修复进展，操作成功并消耗模块。
  - `after.damaged == 0`：完全修复，操作成功并消耗模块。
  - 调用报错或损坏数量完全不变：操作失败并返还模块。
- 不再要求所有自定义 MOD 部件都能恢复，避免玩家获得车辆修复效果后又拿回耗材。

## 验证

- `Test-GodSystemV11663TerminalSync.ps1` 覆盖服务端 payload、`itemId` 定位、页面单次同步、原生字段同步和客户端延迟应用。
- `Test-GodSystemV11663VehicleRepair.ps1` 与运行时脚本覆盖部分有效修复、完全无进展和完整修复三种结果。
- 统一 `tools/Test-GodSystem.ps1`、编码检查、29 个 Lua 的 Lua 5.1 编译、Workshop 文件哈希校验均通过。
- 用户已确认当前 Workshop 测试包通过，并已将 v1.16.63 发布到创意工坊；本轮代码可以推送、合并 `main` 并建立发布标签。

## 后续规则

- MP 动态物品字段不能只依赖普通状态刷新或玩家重新拾取物品；服务端应按实例 ID 下发权威字段，客户端只应用明确回包。
- 页面打开同步只能作为一次补偿路径，主路径仍应是交易成功后的即时回包。
- 付费修理的成功标准应是“是否产生可测量的修复进展”，而不是“所有第三方部件是否全部恢复”。
- v1.16.63 已正式发布，后续版本必须兼容其终端物品、等级、减载核心和多人持久数据。
