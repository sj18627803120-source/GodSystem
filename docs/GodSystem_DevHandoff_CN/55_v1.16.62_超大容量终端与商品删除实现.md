## 超大容量实现

新增 `GodSystem_TerminalCapacity.lua`，在 `ItemContainer` 类方法可用后窄范围包装 `getEffectiveCapacity()` 与 `hasRoomFor()`。

只有子容器所属物品精确为 `GodSystem.SystemSpaceTerminal` 且实例保存了合法目标容量时才走扩展逻辑；其他全部容器调用安装当时捕获的原方法。包装函数每次安装都捕获自己的下层函数，避免与其他 Mod 的前后包装形成递归。

终端底层 `setCapacity()` 仍只写 `min(目标容量, 49)`，规避旧实测中的原生 50 边界；扩展目标写入终端实例 `GodSystemTerminalTargetCapacity` 并放入弱键运行时映射。容量判定只读取常数个字段和当前 `getContentsWeight()`，不遍历库存。

容量表规则：

- 1—8级保持 `10/15/20/25/30/35/42/49` 与原价格。
- 8级以后每级 `+5`，每次固定 `1100` 系统币。
- 可完整按 5 增长且不触及 2000 的最后一级为 Lv.398、容量 1999。
- Lv.398 后无下一等级，客户端和服务端都由同一张生成表重新计算等级、容量与价格。
- 容量值保持精确，不叠加原版容量倍率，防止 1999 被倍率推到参考安全边界之外。

SP 打开/刷新终端时注册本地判定；MP 客户端注册相同显示和转移动作判定，服务端注册并复验权威容量。服务器仍负责升级等级和扣费，应用失败恢复旧等级且不扣币。

## 压缩退役与旧存档迁移

主动压缩已经从配置等级表、SP/MP升级路由、终端按钮与状态、容器变化监听、内容签名和活跃终端实例改重中全部移除。

`GodSystem_LegacyCompressionCleanup.lua` 只承担一次性兼容恢复：识别旧 `GodSystemCompression*` 实例标记，使用保存的原 setter 输入、原有效重量和原自定义状态恢复物品，成功后清除标记。玩家库存和终端各有迁移版本，完成后后续调用为 O(1)；恢复失败保留标记，以便下一次明确状态应用重试。

多人只由服务端执行真实恢复，并对恢复实例调用物品状态同步；客户端不再自行修改多人实例重量。迁移代码绝不调用 `ScriptItem:DoParam()` 或修改共享定义。

## 终端界面

- 只保留“升级容量”和“升级减重”两个属性按钮。
- 容量行显示上限398，减重行仍显示上限8。
- 容量占用读取 `getContentsWeight()` 一次，不对物品逐件扫描。
- 新说明明确Lv.8后每级固定增加5、固定花费1100、上限1999；容量升级不会压缩或改变任何物品重量。
- 物品提示同步更新，不再宣称“Lv.8/最大49”。

## 已上架商品删除

- `GodSystem_ShopVariants.deleteUnlocked(data, variantKey)` 只按精确键删除当前玩家的上架记录。
- 隐藏管理弹窗增加“删除上架”按钮；点击后必须确认，明确“不退款、重新上架需重新付费”。
- SP 使用 `GodSystem.deleteShopItem()`；MP 使用 `deleteShopItem { variantKey }`，服务端从当前玩家数据复验并删除，随后回传完整状态。
- 内置商品不在该管理弹窗中，因此不能被删除。
- 旧 `removeUnlocked` 命令继续仅执行隐藏，避免旧客户端把兼容请求变成永久删除。
- 删除只移除商城上架记录，不删除玩家背包里的原物品，也不改变其他商品记录。

3. 退出读档、死亡重生、丢弃/重新捡起终端后容量和减重恢复。
