## 实现地图

| 模块 | 职责 |
| --- | --- |
| InventoryContext | 一次展开选区，按对象引用去重；保存类型/来源，ID 和家具变体延迟读取；提供浅层归属判断 |
| VehicleRepairContext / MaintenanceContext / AutoLoaderContext / LotteryContext | 世界先判车；库存先判相关类型，再查询相关对象状态；灰色选项有原因 |
| RangeRecycleService | 变更时建立成员集合；纯菜单查询 `getContextMenuState` 返回 enabled/ready/mode/revision/members/token |
| RecycleContext | 小批量原路径，大批量转准备窗口；保持转移动作与完成屏障；转移后校验真实引用 |
| RecyclePreparation / RecyclePreparationUI | 每玩家一个任务，分析/复核/确认/取消，所有本地玩家共享每帧预算 |
| ContextContent | 分步扫描、归并排序、哈希和内容复核；生成与旧签名相同的 `count:hash` |
| InventoryIndex | 验证阶段专用 ID 索引，拒绝歧义 ID，不跨操作保存库存索引 |
| ClientRuntime_Recycle / ServerRuntime_Commerce / Economy 辅助函数 | 每次验证只建一次库存索引，复用配置集合和类型/变体判断；价格仍读真实实例 |

## 行为与安全边界

1. 1–200 件仍显示原快捷菜单和可用数量；普通回收不增加确认，非空容器及仅上架沿用原确认规则。已上架类型不会被错误记为“普通回收跳过”。
2. 201 件起，菜单不做完整分类、精确数量、费用、收益或容器内容分析，也不扫描现金或请求服务器刷新。只保留“批量…”，已关闭功能隐藏，同步中置灰。选择快照本身仍是 O(选中物品数)，不是零成本。
3. 点击后，每帧最多 64 个准备步骤、约 2 ms 协作预算。一个步骤可能是选择项分析、内容扫描、一个归并/哈希条目或复核条目。无法中断单次 Java 调用，因此 2 ms 是协作预算而非硬实时保证。巨型容器也显示检查步骤进度，用户可取消。
4. 分析后先复核，再展示可处理数量、跳过数量、仅上架类型数/费用和非空容器风险。确认后再分帧复核，完成前没有转移动作或网络交易。实际回收收益只在执行端结算，不把预览当权威价格。
5. 检查玩家对象/存活状态、运行配置表与经济版本、数据快照、名单 token、物品 ID/类型/来源/家具变体及容器引用。内容复核检查容器大小、槽位引用、ID/类型、嵌套容器引用及家具变体。取消、退出、断线或变化则释放任务。逐帧复核不是跨帧库存锁；最终客户端和执行端仍重新查找真实物品，执行端重验内容签名。
6. 范围名单的成员集合仅借给内部菜单读取，调用者不得修改；加载、编辑、导入、服务端确认后替换集合和 token。按玩家对象和本次会话隔离；重连/主菜单清空，名单未准备好时不从右键读文件。冷加载在启动/后台 tick 完成，失败最多每 5 秒重试一次。
7. 批量执行的三道索引互不共享：客户端转移完成检查、SP 执行、MP 服务端执行。MP 不信任客户端索引；每阶段遍历各容器一次，再按 ID 查找。保留原生 Remove、删除后核验、装备恢复、来源退款、内容签名和操作 ID 防重。**实际删除、删除核验与发币仍一次结算；未改成跨帧交易。**

## 自动验证

本地测试依赖为 `lupa==2.8` 的 `lupa.lua51` VM，断言 `_VERSION == "Lua 5.1"`。通过 Lua 5.1 的 `loadstring` 编译全部打包 Lua；不是原生 `luac.exe -p`，更不是游戏的 Kahlua/Java 实测。`.test-runtime` 和 `__pycache__` 已忽略，不进入 MOD 打包内容。

可在仓库根目录运行（`python` 指可导入上述测试依赖的解释器）：

```powershell
python -m pip install --target .test-runtime lupa==2.8
python tools/tests/run_lua_tests.py
python tools/tests/run_lua_tests.py --compile-only
powershell -NoProfile -ExecutionPolicy Bypass -File tools/Test-GodSystem.ps1 -SkipLuaCompile
```

已有原生 Lua 5.1 编译器的游戏测试机继续执行 `tools/Test-GodSystem.ps1 -RequireLuaCompiler`。本设备测试依赖目录有访问限制，运行 VM 测试使用经批准的本地执行权限，不需要修改系统执行策略。

本轮结果：

- **23 组行为回归**通过。覆盖 1/200/201/1,000/10,000 件、堆叠/多选/重复引用/家具变体；20,000 种名单缓存、编辑、导入、MP 同步与重连；准备取消、替换、人物/配置/价格变化、等数量内容替换和嵌套容器替换；确认窗口回调；SP/MP 实际批量处理器的删除失败、发币失败、退款、装备/额度恢复及重复请求。

### 性能计数和测量

这些是本机 Lua 5.1 替身测试的一次样本，不是游戏延迟承诺：

| 场景 | 结果 |
| --- | --- |
| 普通地面右键 | 修车模块搜索 0 次 |
| 选中 1 件、库存分别 1/10,000 件 | 菜单库存遍历都为 0 次；ID 读取均为 1 次 |
| 10,000 件大批量菜单 | ID、分类、费用、配置商品集合构建、库存遍历均为 0 次（不含建立选择快照的类型/来源读取） |
| 20,000 种名单，缓存后查询 1,000 次 | 额外名单清洗和文件读取均为 0 次；token 保持不变 |
| 201/1,000/10,000 件，无容器，模拟时钟不推进 | 初次分析+复核分别 7/32/313 次调度；每片不超过 64 步；时间预算另用推进的模拟时钟验证 |
| SP 10,000 件交易 | 索引 1 次/10,000 条/1 个容器，约 11 ms；Remove 替身累计约 192 ms；交易总计约 1,176 ms |
| MP 10,000 件交易 | 索引 1 次/10,000 条/1 个容器，约 13 ms；Remove 替身累计约 152 ms；交易总计约 1,212 ms |

交易总耗时包含保留的删除后逐件核验等成本，不能由“索引一次”推出整个交易 O(N)。原生删除、核验和发币在 B42.20 中的耗时必须单独实测。
