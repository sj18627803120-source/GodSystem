# 42.20_3.8 更新计划

日期：2026-09-14。此计划已按用户确认规则实施；实施细节、验证结果与实机验收项见 `91_v42.20_3.8_实施与验收.md`。源码现为 `42.20_3.8`，未部署、不发布、不替换备份。用户已反馈上一轮复合武器及建议复测流程无问题，见 89。

建议主题：**装备兼容收尾、任务结算完善、常用操作提效**。3.8 主体先完成 P0/P1，商品收藏为可见体验项；新战斗特效另作候选，避免同时扩大多条战斗路径。

## P0：装备缺省耐久分支闭环

**已确认问题**：普通复合武器已修复并获用户验收，但可选耐久路径仍有一个特殊界面分支。

- `GodSystem_EquipmentUI.lua:195` 在 record.durability 缺省时使用空表；246/250 调用 I.full(d)。
- `GodSystem_EquipmentItems.lua:99` 的 I.full 只判断表是否存在，随后比较 condition 与 conditionMax。独立 Lua 5.1 调用 I.full({}) 已复现 `attempt to compare two nil values`。这是特殊缺省状态，不是用户已通过的常规复合武器流程回归失败。
- `GodSystem_EquipmentService.lua:313` 仍给无耐久档案提供找回价格，UI 会先允许点击，再由服务端拒绝。

**计划**：完整区分绑定/培养、修复、找回的可用性与原因；缺省耐久不绘制伪造数值、不比较 nil、不影响特效；找回不可用时禁用按钮并说明原因。保留真实物品身份及权限校验。

**验收**：正常复合武器、高耐久上限、不可读耐久、失踪装备四类都能打开详情；不支持的操作提前说明且不收费；重新载入仍能培养、解绑。增加实际 refreshDetails 路径回归，不能只测服务层。

## P1：任务服务端结算完善

**代码确认**：`GodSystem_ServerRuntime_EconomyTasks.lua:612` 的 claimTaskForPlayer 使用 clientProgress 覆盖服务端计算值，clientExpired 参与失败判定；`GodSystem_ServerRuntime_Services.lua:472` 的手动/自动领取将请求参数传入。当前状态检查存在，但不能代替进度来源验证。

**计划**：

1. 已由服务端记录的消费、购买、回收及时间条件直接采用权威数据；客户端只请求结算。
2. 击杀、移动分别核对 B42.20.4 可用的服务端事件与计数。无法完整观测的类型明确支持边界；处理传送、重连、重生，不能直接用更苛刻阈值导致正常玩家丢进度。
3. 到期由服务端时间判断；接取时的起点也不直接采用客户端绝对值。
4. 奖励发放补齐部分成功、重试、自动/手动同时领取的事务检查与持久回执；当前代码先发奖励再置 claimed，需要专项验证中途失败。此项是代码风险与测试缺口，尚无实际重复发奖报告。

**验收**：正常 SP/MP 进度与奖励保持一致；虚高、过期、重复和乱序请求不会提前领奖、误失败或重复计入装备槽任务数；中途失败不多发、不吞奖励。测试经济上限与多项奖励部分失败。

## P1：负重与装备诊断可读化

**现状**：负重已有模式、当前基础值、最终值及状态；getStatus 未提供下次重试时刻。现有诊断页主要显示网络命令与同步信息。无需重写已通过的负重算法。

**计划**：升级页显示等待自动重试的剩余时间；诊断页补充已知基础值、我们的增量、当前基础/倍率、最后状态变化及原因。装备显示修复/找回不可用原因。提供主动生成的精简诊断文本，避免要求玩家抄整份日志。

**实现约束**：倒计时由本地显示计算，不能每秒发送完整状态包；记录有上限、仅状态变化时追加；不能从数值变动凭空断言是哪一个 mod 写入。诊断文本不导出整份存档或账号数据。

**验收**：玩家能区分“等待同步”“等待重试”“未知改写”；长时间稳定运行不累计无限记录，不新增永久全背包扫描。

## P2：商店常用品与重复操作

**候选增强**：当前已有分类、搜索、分页、购买后保留选中；本轮检查未找到商品收藏/最近购买入口。

**计划**：收藏商品、最近购买列表，保存玩家筛选偏好；优先复用现有商品稳定标识，不以中文名称识别。最近购买仅记录成功交易，不能把打开商品等同购买；失效或禁售商品仍受当前配置与服务端校验。

**验收**：重开界面保留偏好；切分类和购买不跳错商品；大量 mod 商品下不在绘制时遍历整个目录。仅展示快捷入口，沿用原有交易确认及重新报价。
