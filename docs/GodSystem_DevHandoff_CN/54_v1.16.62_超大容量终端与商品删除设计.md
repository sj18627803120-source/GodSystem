# GodSystem v1.16.62 超大容量终端与商品删除设计

## 基线与范围

- 基线：`fix/v1.16.61-shop-visibility@61d5716`。
- 开发分支：`experiment/v1.16.62-large-terminal`。
- 本版删除主动压缩升级与运行时改重功能；保留容量、减重和自动回收。
- 隐藏管理窗口新增真正的“删除上架”操作。删除后不退款，可重新付费上架。
- 不增加空间仓库、额外装备槽、世界容器或全局物品重量修改。

## 参考依据与取舍

1. `BRCrystal(B42.13)` 通过窄范围包装 `ItemContainer:getEffectiveCapacity()` 与 `hasRoomFor()`，并把沙盒容量上限设为 2000。该实现证明容量判定可被替换，但版本较旧，不能直接照搬其全局识别和加载方式。
2. 未标版本的 `BRCrystal` 只在物品脚本中声明 100/150/200 容量，没有动态逐级扩容代码，只能作为“大于 50 的声明容量在部分 B42 环境出现过”的辅助证据。
3. `CultivationStorageArtifacts 42.15` 同时修改物品实例与共享 `ScriptItem` 重量。共享原型修改会影响同类型全部实例，因此不采用。
4. `Unified Carry Weight Framework 42.15` 处理人物最大负重，不处理容器容量；其多人服务端权威模式只用于同步策略参考。

最终采用窄范围覆盖：只识别 `GodSystem.SystemSpaceTerminal` 的子 `ItemContainer`，其他容器始终调用原方法。客户端负责一致的转移/UI判定，服务端使用相同规则复验；容量查询为 O(1)，不新增库存轮询。

## 容量规则

- 1—8级沿用原容量和价格，避免旧存档与经济迁移：10、15、20、25、30、35、42、49。
- 8级之后每级固定增加 5 容量，升级价格固定为 1100，不继续增长。
- 参考实现的 2000 上限作为硬安全边界。为保证每级都完整增加 5，最高为 398级、1999容量；不会生成 2000以上的目标值。
- 等级和目标容量保存在玩家数据与终端实例 `modData`。底层原生 `setCapacity()` 只写入不超过 49 的兼容值；真实判定由系统终端专用覆盖返回目标容量。
- `hasRoomFor()` 使用当前内容重量加待放入物品重量，与专用有效容量比较；参数或实例不可靠时回退原版方法。
- 容量购买仍由服务端重新计算等级、价格并应用后扣费，失败恢复旧等级且不扣币。

## 移除压缩与旧存档恢复

- 删除压缩等级配置、升级路由、按钮、状态、批处理、移动监听和运行时物品改重。
- 新增一次性兼容清理器，只识别旧 `GodSystemCompression*` 标记，根据保存的原重量和自定义重量状态恢复实例并清除标记。
- 清理器仅在玩家/终端相关状态应用时执行；成功后记录迁移版本，不做每帧或分钟级全库存扫描。
- 恢复失败时保留旧标记并在下一次明确刷新重试，不把失败物品继续压缩，也不修改共享 `ScriptItem`。
- 旧 `autoRecyclerCompressionLevel` 不再参与等级、恢复费用、界面或多人状态。

## 商品真正删除

- 隐藏管理窗口增加“删除上架”按钮和二次确认。
- 只允许删除玩家自己的 `unlockedShopItems[variantKey]`；内置商品不会出现在该窗口。
- 单人直接删除持久记录并写历史；多人发送 `deleteShopItem`，服务端按当前玩家与精确 `variantKey` 复验后删除并回传状态。
- 删除不退款，之后可通过正常流程重新上架并重新支付费用。
- 旧客户端的 `removeUnlocked` 兼容入口继续保持“隐藏”，避免旧客户端意外触发永久删除。

## 发布门槛

- 静态专项测试覆盖容量序列、398级/1999上限、8级后固定 1100、窄范围方法包装、压缩路由消失、旧标记恢复、商品删除全链路。
- 运行历史回归、编码检查和可用的 Lua 5.1 编译；缺少环境的项目如实标记未执行。
- B42.19 单人与多人实测必须验证：49以上持续放入、接近1999、重连/重启、超限拒绝、删除/重新上架，以及旧压缩物品恢复。
- 本分支为实验交付，实机门槛通过前不合并 `main`、不覆盖稳定包。
