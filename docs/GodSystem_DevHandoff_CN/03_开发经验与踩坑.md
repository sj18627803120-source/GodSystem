# 开发经验与踩坑

## Superpowers 与子代理边界

后续开发要把 Superpowers 当成默认协作层，而不是临时插件：

- 新功能、UI 大改、多人模式、经济系统、银行/任务/传送等行为变化，先用 `superpowers:brainstorming` 扩散需求，问清范围、验收口径、风险和用户偏好，再决定是否动代码。
- 多文件、高风险或需要分阶段测试的改动，先用 `superpowers:writing-plans` 写计划；计划要能被未来代理按任务执行，包含文件、步骤、验证方式和版本/备份要求。
- 已有计划且任务可以拆开时，用 `superpowers:subagent-driven-development` 执行：主代理负责编排，子代理负责清晰边界内的实现/审查，最后由主代理整合和验证。
- 多个互不依赖的研究或审查任务，可以用 `superpowers:dispatching-parallel-agents`：例如一个代理看同版本参考 MOD，一个代理看原版 B42 文件，一个代理审本地化覆盖，一个代理审包装结构。
- Bug、红字、UI 黑页、多人不同步、任务进度异常、编码乱码、玩家反馈疑似问题时，先用 `superpowers:systematic-debugging`，不要凭直觉直接修。
- 交付前必须用 `superpowers:verification-before-completion`，明确说出跑过哪些检查、结果是什么，没法跑的也要说清楚。

子代理使用边界：

- 子代理适合做独立阅读、参考 MOD 对照、接口调查、风险审查、局部实现和局部复查。
- 不要让多个子代理同时改同一批 Lua 文件；如果必须并行实现，必须提前划分互不重叠的文件或职责。
- 子代理不能替主代理决定最终架构、不能跳过版本迭代、Git 状态复核和编码检查，也不能替代主代理最终验收。滚动 ZIP 只在用户明确要求时生成。
- 给子代理的任务要自包含：告诉它目标、文件路径、版本约束、禁止事项和期望输出，不要让它凭聊天历史猜。
- 子代理返回结果后，主代理要整合、复核、跑检查，再向用户交付。

## 汉化

汉化问题出现过多次，经验如下：

- UI 上尽量不要直接写英文常量，优先走 `GodSystem.text(key, fallback)`。
- `Translate\CN` 和 `Translate\CH` 都要保留，兼容不同中文环境。
- Lua fallback 也要保留，因为有些环境不会正确读取全部翻译文件。
- 当前代码里的 `GodSystem.text()` 会优先读 `GodSystemFallbackText.zh`，也就是 `GodSystem_Localization.lua` 和 `GodSystem_Localization_Override.lua`；因此不能只改 `Translate\CN`。
- `GodSystem_Localization_Override.lua` 是最终覆盖层，后续新增 UI 文本时必须同步补这里。
- `GodSystem_Config.lua` 里的任务模板 `title/description` 也可能作为 fallback 透出，不能留下英文。
- 过长文本不要挤在底部一行，应放详情栏或可滚动说明区。
- 分类名、按钮名、提示语都需要进入翻译表。

## 编码与文件读取

编码问题反复出现，后续按工具结果判断，不按控制台肉眼判断：

- Windows PowerShell 控制台显示中文乱码，不等于文件已经乱码；它可能只是当前代码页/字体显示问题。
- 每次改动 Lua、翻译、脚本、上传说明或说明文本后，运行 `C:\Users\Admin\Desktop\PJ\Test-GodSystemEncoding.ps1` 检查实时 MOD 目录。
- 标准命令：`powershell -ExecutionPolicy Bypass -File 'C:\Users\Admin\Desktop\PJ\Test-GodSystemEncoding.ps1' -Root 'C:\Users\Admin\Zomboid\Workshop\GodSystem'`。
- 需要连文档也检查时可加 `-IncludeDocs`，但旧交接文档可能保留历史乱码证据，不能把旧记录误判为本轮新增问题。
- `GodSystem_Localization_Override.lua` 是游戏内 fallback 关键路径；新增中文运行时文本优先写成 UTF-8 十进制字节转义，例如 `\229\...`，避免 PZ/Lua 加载路径或编辑器编码差异造成游戏内乱码。
- `Translate\CN/CH` 和 Markdown 交接文档可以直接写 UTF-8 中文，但写完仍要跑编码检查，重点排查 U+FFFD 和常见 mojibake 片段。

## 第三方 MOD 独立汉化补丁经验

2026-06-28 处理 KnoxSurvivorsCN 时补充：

- B42 同版本 MOD 可能同时支持 `Translate\CN\ui.json` 和旧式 `Translate\CN\UI_CN.txt`。原 MOD 如果自带 `Translate\EN\UI.json`，独立汉化补丁只放 `UI_CN.txt` 可能会出现“日志显示加载但游戏内无效果”。稳妥做法是同一批 key 同时生成 `ui.json`、`sandbox.json`、`ig_ui.json` 和对应 `_CN.txt`。
- 专用汉化补丁要确认实际启用目录和工作区源目录一致。`C:\Users\Admin\Zomboid\Workshop\...\Contents\mods\...` 改好了，不代表 `C:\Users\Admin\Zomboid\mods\...` 已同步；用户本地测试通常读后者。
- 独立汉化补丁如果和大型总汉化包一起启用，最好让专用汉化补丁在存档 `mods.txt` 和默认列表里排到总汉化包之后，否则后加载的总汉化资源可能覆盖同路径 `cn/ui.json` 或 `cn/ui_cn.txt`。
- 避免在 Lua 桥接文件里直接写中文。对需要拦截硬编码英文菜单的补丁，Lua 保持 ASCII-only，通过 `getText("UI_xxx")` 读取 Translate 文件中的中文。
- 右键菜单桥接不要只在 `OnGameStart` 尝试一次。`ISContextMenu` 可能尚未就绪，应在 `OnCreatePlayer`、`OnFillWorldObjectContextMenu` 也重试，并打印 ASCII 诊断日志，例如 `bridge loaded`、`context menu patched`、`probe UI_xxx=hit/miss`。
- 如果用户决定取消订阅并本地化原 MOD 本体，先把 Workshop 原 MOD 完整复制到 `C:\Users\Admin\Zomboid\mods\<ModId>`，再备份初始 zip；随后只启用本体 `ModId`，移除旧独立汉化补丁的启用项，避免本体汉化和补丁汉化互相覆盖。
- 本体汉化仍然不要在 Lua 里直接写中文。可在本体 client 下新增 ASCII-only 桥接 Lua，例如 `KS_CN_LocalizationPatch.lua`，负责把硬编码英文菜单、窗口按钮和 panel 行转成 `getText` key；中文文本继续放在 `Translate\CN\*.txt/json`。
- 不要用会隐式转码的 PowerShell 字符串批量改中文；优先用 `apply_patch` 小范围编辑，或用明确 UTF-8 的读写脚本。

## UI

UI 已经重构为左侧导航、顶部状态、中央列表、右侧详情、底部动作栏。

后续新增功能必须遵守：

- 左侧功能按钮纵向追加，不要写死位置。
- 底部动作按钮统一走动作栏布局，不要在各页面单独硬编码横坐标。
- 搜索框、分类框、购买、刷新等都放动作栏，避免遮挡列表。
- 主窗口当前为固定 `1240x690` 大面板，不再支持主窗口缩放；后续优化应优先在固定画布内用半自动布局和短文案处理，而不是恢复自由缩放。
- 固定画布内仍不要在各页面随手写死散落坐标；页面布局要从主题和 `setupLayoutMetrics()` 计算，方便后续继续微调。
- 主窗口布局统一走 `setupLayoutMetrics()` + `applyBaseLayout()` + `setActionBar()`：导航、主列表、详情栏、任务双列、底部按钮都必须使用这些指标，避免各页面自己写死坐标。
- 底部动作栏保持单行，不换行；宽度不够时按比例压缩按钮并截断标题。
- 字体不要做连续缩放，避免 PZ UI 字体发糊和按钮高度混乱；只做布局自适应。
- 任务追踪窗口也要可缩放，宽高保存到 `data.ui.taskTrackerW/H`；不要每帧强制回固定高度，否则玩家手动拉伸会失效。
- 任务追踪列表应根据窗口宽度动态分配标题列和进度列，避免 `500/500 剩21h` 这类文本被固定 96px 宽度截断。
- 列表文字太长时截断，完整说明放右侧详情。
- B42 `ISScrollingListBox:clear()` 只清 `items/count/selected`，不会重置 `YScroll`、`scrollHeight` 或 `smoothScrollTargetY/smoothScrollY`。GodSystem 复用同一个列表控件切页时，重建前必须走 `resetScrollingListState()`；否则可能出现商店/天赋“右侧详情和右键菜单正常，但中间列表黑屏/空白”的假象。
- B42 `ISScrollingListBox` 的 `vscroll` 是子控件，初始化时才按父列表宽高设置 `x = parent.width - 16` 和 `height = parent.height`；之后调用父列表 `setWidth/setHeight` 不会自动重贴滚动条。原版 `ISScrollingListBox:prerender()` 在滚动条可见时会用 `self.vscroll.x + 3` 作为 stencil 宽度，旧 `vscroll.x` 可能把长列表绘制区裁成极窄或黑屏。GodSystem 的 `gsSetBounds()` 必须在改宽高后调用 `gsSyncScrollingListGeometry()`，同步 `vscroll.x/y/height` 并 `updatePos()`。
- 如果某页“少量分类正常、全部分类/天赋/回收/任务/腰包长列表黑屏，输入搜索词变少后又出现”，优先怀疑滚动条几何和 stencil 裁剪，而不是数据丢失。
- v1.16.23 起 GodSystem 自己创建的三个滚动列表 `self.list/self.detailList/self.activeList` 都必须安装 `gsSafeScrollingListPrerender()`；该 wrapper 在原版 `ISScrollingListBox.prerender()` 前后都调用 `gsSyncScrollingListGeometry()`。不要只修商城、回收、天赋，任务双列、腰包空间、升级页、右侧详情长文本同样会在出现滚动条时触发。
- 自定义列表行绘制不要只依赖原版 item wrapper 的 `item.text`；`addListItem()` 应把显示文本同时存到 payload，例如 `payload.displayText`，`drawListItem()` 再按 `item.text -> payload.displayText -> payload.label` 兜底。

## 货币与 B42 物品脚本

一开始用 ModData 点数，担心玩家重进后数据回到初始，因此改为系统币物品。

系统币是实际物品：

- `GodSystem.SystemCoin1`
- `GodSystem.SystemCoin10`
- `GodSystem.SystemCoin100`

当前稳定版 v1.15.3 重要修复：

- 系统币脚本改为 B42 原版风格 `ItemType = base:normal`。
- 补 `WorldStaticModel = Money`。
- 用户已实测：不启用 `that DAMN Library`，只启用 GodSystem 也能正常进游戏。

曾经的红字根因：

- `GodSystem_Core.lua` 发系统币时调用 `inventory:AddItem(fullType)`。
- B42.19 下系统币脚本缺少正确 `ItemType` 时，`AddItem` 创建出 nil item，Java 层后续调用 `setAlcoholPower` 出现 NPE。
- 开启 `that DAMN Library` 后变正常，是因为它有 fallback 脚本给缺失 `ItemType` 的物品补 `ItemType = base:normal`。
- 这说明 GodSystem 不需要依赖 `damnlib`，只需要自己把物品脚本修正确。

后续新增自定义普通物品：

- 优先写 `ItemType = base:normal`，不要只写旧式 `Type = Normal`。
- 优先参考 B42 原版或参考 MOD 的 B42 分支脚本字段。
- 如果 `AddItem(fullType)` 出现 nil 或 Java NPE，第一时间检查物品脚本字段、模块名、`fullType` 和 `getScriptManager():FindItem(fullType)`。

如果玩家仍然红字，先查是否存在重复安装：

- Workshop 订阅旧版
- 本地 `Zomboid\mods` 旧版
- Workshop 上传测试目录残留
- 同名 `GodSystem` 多份同时启用

## 参考 MOD 优先原则

后续开发不要直接凭记忆写 PZ 接口。固定流程：

- 先确认当前目标版本。当前 GodSystem 稳定目标是 B42.19。
- 如果有 B42.19 官方开发手册、官方示例或当前版本原版脚本，官方同版本资料第一优先。
- 再在 `C:\Users\Admin\Desktop\PJ\File` 找同版本同类参考 MOD。
- 先读官方/参考 MOD 的目录结构、事件注册、脚本字段、UI 控件、容器/物品 API。
- 再改 GodSystem。
- 每次发现新的接口、坑、稳定结论，都追加到 `08_参考MOD研究笔记.md` 或本文件。

参考优先级：

1. 同版本官方开发手册 / 官方示例 / 当前版本原版脚本。
2. 用户提供的同版本参考 MOD。
3. 其他同版本社区 MOD。
4. 不同版本官方资料。
5. 不同版本 MOD 或旧教程。

总原则：谁的版本和当前开发版本一致，谁优先级更高；同版本时官方最高。

当前已确认：

- `damnlib` 解释了 `ItemType` 缺失问题，但不要打包它。
- `RuinBazaar` 可参考“数据表 + 交易管理器 + UI 分离”的结构。
- `TraitsPurchaseSystem` 后续天赋功能优先参考。
- `DebugMenu` 可参考调试发物品接口。
- `Server Shop\42.19` 可参考 B42.19 多人服务器商店分层、服务端权威交易、离线发货和审计日志。

## v1.16.45 腰包模式与中文底层治理经验

- 腰包回收模式必须和普通回收页模式分离：普通回收页继续用 `recycleUnlockMode`，腰包页用 `waistRecycleUnlockMode`。缺失字段默认 `false`，保证老玩家升级后仍是“仅回收”。
- 腰包相关入口必须共用同一个模式判断：手动选中、手动全部、快捷栏“卖腰包”、单人自动腰包回收、多人自动腰包回收都应走 `recycleWaistSpaceItemsByMode()` 或等价服务端命令选择，不要在各入口各写一套判断。
- 多人提示不要从服务端发送中文整句。参考同版本多人 MOD 的稳定做法，本轮触及路径改为服务端发 `{ code, args }`，客户端用 `NotifyMP_*` 本地化；旧 `message` 只能作为兼容 fallback。
- 运行时中文 key 要用生成流程维护：先改 `tools/godsystem_v11645_localization.yml`，再运行 `tools/generate_godsystem_v11645_localization.py` 同步写入 `Translate\CN`、`Translate\CH` 和 `GodSystem_Localization_Override.lua`。
- `GodSystem_Localization_Override.lua` 新增中文 fallback 必须保持 ASCII-only UTF-8 字节转义。`Translate` 和 Markdown 可以是 UTF-8 中文，但要跑编码检查和专项测试。
- PowerShell 控制台显示 mojibake 不是文件损坏证据。判断中文是否真坏，要用显式 UTF-8 读取、扫描 `U+FFFD` 和常见 mojibake 片段，不能凭控制台肉眼判断。
- 低风险清理要有静态证据：重复 `Commands.*`、协议无 handler、实时 Lua 中废弃命名残留可以处理；历史文档里的事故记录不要当作代码残留删除。

## 多人模式适配

2026-06-15 已研究 `C:\Users\Admin\Desktop\PJ\File\Server Shop\42.19`，结论如下：

- MP 下客户端不能作为可信经济逻辑。UI 只负责发请求和显示结果，扣钱、发物品、删物品、任务奖励、传送扣费都必须由服务端重新校验。
- 服务端 Lua 文件应放在 `media\lua\server`，开头用 `if not isServer() then return end`；客户端入口用 `if not isClient() then return end`。
- 固定通信模式：客户端 `sendClientCommand(player, module, command, args)`，服务端 `Events.OnClientCommand.Add(...)` 分发到命令表；服务端再 `sendServerCommand(player, module, command, args)` 回包。
- 打开/关闭 UI 时如果注册 `Events.OnServerCommand`，要先 `Remove` 再 `Add`，关闭时也要 `Remove`，避免重复监听。
- 服务端命令不能信任客户端传来的价格、奖励、余额、物品价值或管理员身份；客户端最多传商品 id、操作类型、数量、目标槽位等最小参数。
- 服务端发物品后要优先调用 `sendAddItemToContainer(inv, item)` 同步；删除容器物品后要优先调用 `sendRemoveItemFromContainer(container, item)` 同步。
- 对“兑换券/回收/交任务”这类删除物品再发奖励的逻辑，服务端要先定位真实容器，再标记处理中或已处理，最后删除并发奖励，防止延迟/连点造成重复收益。
- 玩家上线相关逻辑不能只依赖 `OnCreatePlayer`。Server Shop 额外用客户端 `OnTick` 发送一次 `hello` 握手，用来处理 MP 下玩家对象/网络状态未完全就绪导致的离线发货漏触发。
- 管理员功能必须在服务端用 `player:isAccessLevel(...)` 判定，客户端隐藏按钮只是体验优化，不是权限控制。
- 服务器经济功能应加审计日志，使用 `getFileWriter("/path", true, true)` 可写入 `Zomboid/Lua/...`，便于服务器排查异常。
- `ModData.getOrCreate(module)` 适合服务端持久状态；如果是按账号数据，key 优先用 `player:getUsername()`，没有用户名时再 fallback 到 `getOnlineID()`。
- 如果保留实体系统币经济，MP 第一阶段不要急着改成虚拟余额；更稳的是先把“实体币扣除/发放/同步”服务端化，再评估是否需要服务器钱包。

## 回收经济

当前回收价：购买价的 1/20，保底 1 币。

原因：

- 子弹、杂物、书籍等数量巨大，回收比例过高会经济爆炸。
- 完全没有保底会让玩家觉得很多东西没有价值。
- 1/20 由用户实测后反馈手感不错。
- v1.16.19 起，散装弹药回收值固定为 1 币，不再按通用 Ammo fallback 价回收。判断规则覆盖 `item:getCategory() == "Ammo"`、价格分类 `ammo`、以及 fullType 包含 `Bullets` / `ShotgunShells` 的物品；但包含 `Box`、`Carton`、`Clip`、`Magazine`、`AmmoBox`、`Strap`、`Case`、`Bag_` 的盒装、箱装、弹匣、弹药箱、弹带和容器不视为散装。
- 这个规则是为了压制盒装弹药拆开后套利，不追求精确计算“每盒能拆多少发”。客户端和服务端必须保持一致，否则单人/多人回收显示和结算会分叉。

## 活期优先支付

- v1.16.25 起，正常系统消费的“可支付余额”不是单纯背包实体系统币，而是 `银行活期 + 背包实体系统币`。实际扣款顺序为先扣活期，不足再扣背包现金；死期不参与直接支付。
- 单人 `GodSystem.canAfford()` 和 `GodSystem.addPoints(负数)` 已改为走 `GodSystem.getSpendableBalance()` / `GodSystem.spendCurrency()`；多人服务端也有对应 `spendableBalance()` / `spendCurrency()`。
- 多人客户端 `GodSystem_Network.lua` 会覆盖部分单人函数。经济规则改动时不能只改 `GodSystem_Core.lua` 和 `GodSystem_Server.lua`，还要检查网络桥覆盖层，例如 `canAfford()`，否则客户端会只看背包现金并提前误报钱不够。
- 银行存入活期、现金存死期、任务失败罚金不是普通消费：存入活期和现金存死期必须继续只扣背包实体币；任务失败/死亡罚金按既定规则先扣活期，不足再扣身上现金，但不会扣成负数。
- 后续如果再做娱乐玩法，必须先单独原型、单独测试，不能混入经济底盘版本。
- 新增运行时中文 key 时，`GodSystem_Localization_Override.lua` 优先用 UTF-8 十进制字节转义；`Translate\CN/CH` 和 Markdown 可以直接 UTF-8。不要只看 PowerShell 控制台显示来判断是否乱码。

## 腰包自动回收

2026-06-14 新增开发中功能：系统腰包自动回收开关。

设计结论：

- 功能只属于系统回收腰包，不扫描玩家主背包，也不扫描其他容器。
- 自动回收只处理系统腰包第一层物品，行为等同腰包页“一键出售全部”。
- 解锁费用 100 系统币，解锁后开关免费。
- 解锁后默认开启；再次点击按钮可关闭，再次点击可开启。
- 间隔为 1 游戏小时。
- 自动回收必须复用或等价于 `GodSystem.recycleWaistSpaceItems(nil)`，不能走 `GodSystem.recycleInventoryItems()`。
- 原因：`recycleInventoryItems()` 在“解锁上架”模式下会解锁商城单品；腰包自动回收按用户要求不解锁商城。
- 没有可回收物时不要每小时弹“没有可回收物品”，要先用 `getWaistSpaceRecycleGroups()` 判断有内容再调用出售逻辑。

## 家园/传送

2026-06-14 修正传送误判与出发点管理：

- `gsTeleportBlockedReason(player)` 不再检查 `isPlayerMoving/isMoving/isRunning/isSprinting` 或 `getLastX/getLastY` 坐标差。

## v1.16.2 UI 与多人稳定性经验

- 用户测试反馈：单人基本正常，但商店、任务、背包空间等页面偶发打开为空，需要重开 UI；多人回收/购买/一键出售正常，击杀不发币，任务页左侧可接任务闪一下消失，右侧进行中任务难以选择。
- 根因方向：UI 渲染函数里不应触发服务端刷新或任务生成。尤其 `populateTasks()` 在多人桥接后调用 `GodSystem.generateDailyTasks(false)`，等价于向服务器发 `refresh`，会造成任务列表边画边刷新、闪烁和选择丢失。
- 修复原则：打开窗口/切页时只后台请求一次 state；当前页面先渲染已有数据，等服务器 `state` 回来再重画。不要在 `notify/result` 回包里额外刷新 UI，避免一次操作触发 2-3 次重画。
- 多人任务页只显示服务器 state，不在客户端生成/刷新任务；单人仍保留原 `generateDailyTasks(false)`。
- `clearList()` 不再每次重画都强制 `selectedTaskList = "open"`，否则右侧进行中任务刚选中就会被刷新回左列。
- 多人击杀奖励为稳定可用，参考 Server Shop 的做法：客户端定时同步本地 kill 计数给服务端，服务端按差值发实体系统币。当前目标不是强反作弊，而是避免多人 kill 计数服务端读不到导致完全不给钱。

## v1.16.3 UI 状态同步经验

- 用户继续反馈：游玩过程中打开 UI 或来回切换页面，有时某个页面内容消失，重新打开 UI 后恢复。
- 根因方向：多人命令发送后如果客户端立刻 `populateList()`，会用服务器尚未回包的旧状态/空状态重画页面；打开窗口和切页同一帧也可能遇到物品栏或服务器 state 尚未准备好。
- 修复原则：多人模式要先确认收到过服务器 `state`。未收到时显示“正在同步服务器数据”，不要把空数据当成真实页面。
- 多人按钮命令发送后不要立刻本地重画业务页面；统一走 `finishMultiplayerCommand()`，等待服务器 `state` 回包后由 `GodSystem_Network.refreshOnTick()` 刷新。
- 手动刷新按钮在多人模式下应强制请求服务器 state 并等待回包，不应立即按旧数据重画。
- 任务/商店/回收/腰包等列表重画前要按 payload id 捕获当前选择，重画后按 `taskId/fullType/id` 恢复选择。任务页特别要保留右侧 `selectedTaskList = "active"`，避免结算错任务。
- 打开窗口和切页后可以安排 1 tick 延迟补画，覆盖 UI 初始化帧或物品栏数据晚一帧准备好的情况；不要把这个机制用于高频按钮连点结算。

## v1.16.4 记录/说明页与多人文本经验

- 用户测试反馈：单人暂未发现业务问题，但记录和说明页仍偶发内容丢失/变黑；多人记录全是乱码，说明正常，击杀僵尸给钱但没有提示。
- 记录/说明页不需要右侧详情栏。继续复用双栏布局时，快速切页/缩放/刷新会让右侧详情栏清空，看起来像内容变黑。v1.16.4 改为单列文本页，并隐藏 `detailList/detailHeaderLabel`。
- 记录/说明这类长文本不要只依赖列表单行截断，应在主列表里用 `gsWrapText()` 包成多行，避免缩放后文字被压没。
- 多人服务端不要把整句中文写进 `data.history` 再传给客户端。v1.16.4 改为 `{ code = "...", args = {...} }`，客户端 `formatHistoryEntry()` 读取 `HistoryMP_*` 本地化模板显示。
- 商品/任务历史尽量传稳定 id：任务传 `taskId/sourceId`，客户端用 `GodSystem.getTaskTitle()` 本地化；商店传 `shopId/items`，客户端用 `GodSystem.getShopLabel()` 本地化。

- 旧存档中已经写入的乱码历史不要自动清洗或删除，避免误删玩家记录；新产生的历史应不再乱码。

## v1.16.5 多人轻同步与客户端优先经验

- 用户明确要求：防作弊不是 GodSystem 当前优先级，兼容性和低性能压力优先；能信客户端就信客户端，涉及真实物品收发/删除时再由服务端做轻验证。
- 多人 UI 不应在切页时请求服务器 state。`GodSystemWindow:onModeButton()` 只切换本地页面和延迟补画，避免“切页 -> refresh -> 旧 state/空 state 回包 -> 页面闪空”。
- 多人同步节奏定为：打开 UI 同步；购买、卖出、回收、任务、传送、天赋等关键操作后同步；后台每 5 分钟现实时间同步一次。后台同步如果遇到关键操作 pending，先让关键操作完成，下一轮再同步。
- 多人主界面手动刷新按钮应隐藏。商店、回收、天赋、升级、家园和同步占位页不再暴露普通刷新按钮；任务“刷新未接取任务”是付费功能，不能当作手动同步按钮移除。
- 多人余额显示优先扫描客户端本地背包实体系统币，服务端 `data.balance` 只做 fallback。这样捡钱/丢钱后 UI 数字能本地变化，买卖时服务端仍扫描真实背包验证是否够钱。
- 击杀奖励改为客户端批量上报：达到 10 击杀、打开 UI、关键/后台同步时 flush。服务端不再后台读取 `player:getZombieKills()` 主动结算，避免频繁 state 刷新。
- 多人任务进度：交物品任务服务端继续检查并移除真实物品；击杀、移动距离、存活、消费、购买、回收等非物品任务使用客户端上报的 `clientProgress`。任务超时由客户端计时，到期后发送 `clientExpired=true`，服务端执行失败与扣罚。
- 多人网络桥接管了原 `GodSystem.onPlayerUpdate` 后，仍要在 `GodSystemNetwork.onPlayerUpdate()` 中定期调用 `GodSystem.updateMoveDistance()`，否则移动距离任务本地进度不会增长。
- 提示使用 `GodSystem.notify()` 队列化，避免多人短时间多条 `player:Say()` 互相覆盖导致“提示不全”。默认间隔 1600ms，可由 `GodSystemConfig.NotifyQueueIntervalMs` 调整。
- 隐藏测试入口：连续点击“说明”页签 5 次，弹出输入框；输入 `12130` 后单人调用 `GodSystem.addPoints(10000)`，多人发送 `debugGrant` 命令由服务端发放 10000 实体系统币。这个入口用于测试，不在普通说明文本里展示。

## v1.16.6 协议、交易与诊断优化经验

- 新增 `media\lua\shared\GodSystem_Protocol.lua`，集中定义 `Module`、C2S/S2C 命令名、需要 state 的命令、关键操作命令和同步节流参数。后续新增多人命令先改协议表，再改客户端 wrapper 和服务端 `Commands`。
- 多人关键操作增加 pending 锁：购买、回收、腰包、任务、传送、天赋、抽奖、测试发币等命令发送后，客户端等待服务端 `result/state` 回包再允许下一条关键操作。这样能降低延迟下重复点击、旧 state 刷新和页面乱跳。
- 关键操作成功发送后不要额外调用普通 `refresh`；服务端操作本身会 `finish()` 并发送 `result + state + notify`。额外刷新容易造成旧数据插队或页面闪动。
- 服务端 `finish()` 顺序调整为先发 `result` 清理客户端 pending，再发 `state` 刷新缓存，最后发 notify。客户端收到 error/result 时会清 pending。
- 服务端实体系统币扣除从“删除所有币再按差额找零”优化为“尽量精确扣除面额，必要时删除更大面额并找零”。这能减少多人背包物品变化数量和同步闪烁。
- 新增诊断页签：显示 SP/MP、客户端 `stateSerial/pending/lastCommand/lastResult/lastError`、服务端 `handledCommands/failedCommands/lastCommand/lastError`。以后用户反馈页面空白、提示丢失、买卖无响应时，优先让用户打开诊断页截图或描述字段。
- 服务端仍尽量避免发送中文整句作为长期数据；新错误应优先使用 `errorCode/notifyCode`，客户端通过 `NotifyMP_*` 本地化显示。临时 `finish` 文本只做提示，不作为存档历史来源。

## v1.16.7 pending 超时兜底经验

- 多人关键操作 pending 锁必须有超时兜底；否则一次服务端回包丢失或事件链异常，就可能让客户端长期卡在“操作处理中”。
- 当前超时阈值放在 `GodSystem_Protocol.lua` 的 `KeyCommandTimeoutMs = 15000`，客户端超过 15 秒未收到 `result/error` 会解除 pending、提示重试，并主动发一次 `refresh`。
- 诊断页显示 `pendingElapsed`、`pendingTimeouts`、`lastPendingTimeoutCommand` 和 `pendingClearReason`。测试时如果操作失败但没报错，优先截图/记录这些字段。
- 超时兜底只保护客户端锁，不代表服务端操作一定失败；如果 15 秒后服务端才处理完，可能出现“已完成但客户端已允许重试”的边缘情况。当前选择是兼容性优先，避免 UI 永久卡死。

## v1.16.8 击杀任务与系统币经验

- 不要用 `player:getZombieKills() - task.startKills` 作为长期任务进度的唯一来源。玩家死亡/重生后角色总击杀数可能归零，旧任务的 `startKills` 仍是死亡前数值，进度会被夹到 0 并一直卡住。
- 击杀任务应保存独立累计字段 `task.killProgress`。检测到击杀数正向 delta 时给所有进行中的击杀任务累加；检测到击杀数下降时只重设基线，不清任务进度。
- 多人为了降低压力可以批量上报击杀，但死亡前未达到同步阈值的 `pendingKillDelta` 必须在 `Events.OnPlayerDeath` 里强制上报，否则玩家杀了几个就死会丢这段任务进度。
- 多人 state 不能盲目覆盖客户端本地更高的击杀任务进度；收到服务端 state 时要按 `taskId` 合并，保留本地更大的 `killProgress`，避免 UI 进度回退。
- 系统币是实体物品，不是银行余额。玩家死亡后系统币可能在尸体/掉落容器里，看起来像“余额没了”。这不是代码吞币，但需要后续说明或考虑“保险余额/银行”设计。
- 代码层面的扣币必须支持回滚。无论单人还是多人，扣除实体货币后如果找零失败，应尽量补回已移除货币，不要返回成功。
- 多人服务端余额统计必须和客户端/扣币扫描口径一致，递归扫描背包内子容器；否则系统币放进包中包时，客户端看得到、服务端余额可能看不到。

## v1.16.10 本地化与 UI 显隐经验

- `GodSystem.text()` 会优先读取 `GodSystem_Localization_Override.lua` 里的 `GodSystemFallbackText.zh`，所以新增 UI 文本如果只改 `Translate\CN/CH`，游戏内仍可能显示旧 fallback。
- 在 Lua fallback 覆盖表里新增中文时，优先使用 `\229\...` 形式的 UTF-8 十进制字节转义。直接写中文在某些 PZ/Lua 加载路径下会变成乱码，银行页这次就是这个问题。
- 标准翻译文件 `Translate\CN/CH` 可以保留直接中文，但运行时关键覆盖层仍是 `GodSystem_Localization_Override.lua`。新增银行、任务、提示、历史等文本必须两边都检查。
- UI `setVisible()` 必须传明确 boolean，不能传 `nil`。`gsIsMultiplayer()` 这类包装函数要保证返回 `true/false`，否则诊断页等早期加载路径会触发原版 `ISButton:setVisible` 报错。

## v1.16.11 多人天赋经验

- B42 同版本 `TraitsPurchaseSystem` 的服务端版证明：多人购买天赋后，服务端可以在 `player:getCharacterTraits():add(trait:getType())` 成功后读取 `trait:getXpBoosts()`，循环 `player:LevelPerk(perk)`，并通过 `player:learnRecipe(recipe)` 补发配方。
- GodSystem 单人路径已有 `gsApplyTraitBenefits()`，但它只在客户端本地 `GodSystem.setPlayerTrait()` 中执行；多人网络桥会把天赋操作改成服务端命令，因此服务端必须补齐同等效果。
- 不要同时在服务端和客户端都自动补发同一个天赋技能，否则可能导致 `+1` 被加成两次。当前 v1.16.11 只在服务端补发，客户端只刷新 state/UI。
- 如果后续玩家反馈“服务端诊断显示 `lastTraitBenefitsOk=true` 但角色面板没刷新”，再考虑添加客户端只刷新角色面板/技能 UI 的逻辑，而不是客户端再次 `LevelPerk`。

## v1.16.12 多人移动任务经验

- 移动距离任务和击杀任务一样，不能让服务端较旧的 `state` 直接覆盖客户端本地进度。否则 UI 会显示不计数、进度回退，提交任务时 `clientProgress` 也可能被旧 `stats.moveDistance` 算成 0。
- 多人客户端接管原 `GodSystem.onPlayerUpdate()` 后，必须在 `GodSystemNetwork.onPlayerUpdate()` 中继续定期调用 `GodSystem.updateMoveDistance()`；此外在领取、提交、超时、死亡、刷新前要主动 flush 一次移动采样。
- `mergeLocalTaskProgress()` 应同时保护任务进度和移动采样点：`stats.moveDistance`、`lastMoveX`、`lastMoveY`、`lastMoveZ`。只保留总距离不保留采样点，会导致下一次 state 覆盖后少算一段路。
- 在“完全信任客户端”的 MP 策略下，服务端不应同时后台累加移动距离；服务端只在 `refresh` 和 `task claim` 接收客户端移动数据，并用于持久化和下一次 state 输出。
- 物品提交任务仍然不能信客户端数量，必须服务端扫描并移除真实物品。移动、击杀、存活、消费、购买、回收统计这类非物品进度可以信 `clientProgress`。

## v1.16.13 钱币整理与腰包自动回收经验

- 银行“钱币整理”是手动功能，不要在击杀奖励、回收、任务奖励、银行取款等路径自动触发。用户明确要求除了既有找零逻辑和银行手动按钮外，不再新增自动整理。
- 整理范围必须和当前可买卖余额扫描一致：玩家背包递归、包含随身/穿戴容器；不扫描地面、车辆、公共箱子。否则会出现“整理了不属于当前玩家随身可用的钱”的争议。
- 单人可本地删除实体系统币后用 `GodSystem.giveCurrency(total)` 重发大面额，并在失败时恢复已删除币；多人必须发 `consolidateCurrency` 给服务端，由服务端验证真实物品、删除、重发并结构化通知。
- 新增 MP 提示/历史时优先用 `{ code, args }`，客户端通过 `NotifyMP_*` / `HistoryMP_*` 本地化。不要从服务端发送中文句子，否则很容易再次出现乱码。
- 多人腰包自动回收不再由服务端每次 `OnPlayerUpdate` 后台轮询执行；改为客户端按游戏小时触发 `recycleWaist`，服务端只在收到命令后验证系统腰包和真实物品。这样符合“尽量本地计时、关键物品操作服务端验证”的轻同步策略。
- 客户端自动触发前要检查是否已有 `pendingKeyCommand`，避免自动腰包回收和玩家手动购买/银行/传送等关键操作撞在一起。

## v1.16.14 固定尺寸 UI 与弹窗经验

- v1.16.14 已失败废弃，不能作为后续 UI 基线。用户测试表现为：除了少数图标，不显示任何文字，红字持续报错。
- 最高概率根因是 Lua 多返回值参数错位：`drawText(text, x, y, gsTextColor(color), UIFont.Small)` 里 `gsTextColor()` 处在参数中间时只会展开第一个返回值，导致实际参数变成 `drawText(text, x, y, r, UIFont.Small)`，PZ `drawText` 需要 `r, g, b, a, font`，所以自绘文字每帧报错。
- 后续 UI 重制禁止使用 `drawText(..., gsTextColor(...), font)` 这类写法。文字绘制必须显式传 `r,g,b,a,font`，或走安全 wrapper，例如 `gsDrawText(ui, text, x, y, color, font)`，由 wrapper 拆 `color.r/g/b/a`。
- v1.16.14 的“固定尺寸暗金风格、主题配置、图标导航、GodSystem 自有弹窗换肤”只能作为设计想法参考，不能直接复用其实现。
- 本轮放弃主窗口缩放改固定尺寸的方向已被撤回；v1.16.15 改为基于 v1.16.13 保留可缩放窗口，仅做保守暗金主题化。
- 窗口尺寸、是否记忆位置/大小、边距、导航宽度、按钮高度、行高、详情栏宽度、状态块尺寸、页签顺序和图标路径可以集中在 `GodSystem_UITheme.lua`，但主题值必须通过安全访问函数进入绘制层。
- 主窗口只记忆位置，不记忆大小；打开时按屏幕边界夹紧，避免低分辨率下窗口跑出屏幕。任务追踪窗口仍保留独立缩放，因为它是常驻小浮窗，和主系统面板需求不同。
- 参考图的“暗金、金属、面板噪声、图标导航”可以用 `media/ui/GodSystem` 下自绘 PNG 资源承载；不要直接打包 AI 参考图原图。当前资源包括徽记、面板噪声和各页签图标。
- GodSystem 自己触发的标准确认/提示弹窗必须通过 `gsShowModalDialog()` 创建，再由 `gsStyleModalDialog()` 做实例级换肤。不要全局替换 `ISModalDialog`，否则会影响游戏本体或其他 MOD 的睡觉、交易、管理面板等弹窗。
- 隐藏测试码输入、银行金额输入这类自定义弹窗走 `ISCollapsableWindow` 派生类，并调用 `gsStyleCollapsableDialog()`、`gsRenderDialogFrame()`、`gsStyleTextEntry()`，保证输入框、小窗标题、按钮风格和主 UI 一致。
- 长文本页如记录、说明、诊断仍保持单列包行显示，不要为了视觉统一强行塞进双列详情布局；此前黑页/内容丢失问题已经证明这些页面更适合单列。
- 弹窗换肤只覆盖 GodSystem 拥有的实例，不接管游戏/其他 MOD 的系统弹窗。若后续需要更强的弹窗视觉控制，应新增 GodSystem 专用确认框类，而不是 monkey patch 原版全局类。

## UI 原型工作流

- 复杂页面先做本地 HTML/CSS 原型，再移植到 PZ Lua。HTML 原型用于快速看布局、比例、颜色和状态，不直接作为最终实现。
- 原型必须主动限制在 PZ Lua/ISUI 容易实现的能力内：固定尺寸、矩形面板、简单边框、纹理图、图标、列表行、进度条、按钮 hover/selected/disabled 状态。不要把浏览器特效当成必须落地的设计，例如毛玻璃、复杂阴影、动画、响应式网格。
- 原型尺寸默认对齐当前主窗口 `1220x690`；颜色、间距、行高、详情栏宽度、导航宽度优先从 `GodSystem_UITheme.lua` 取值，再在原型里微调。
- 每个原型确认后必须同时输出移植规格：颜色表、尺寸表、组件状态、任务/商店/银行行布局、右侧详情分区，以及应修改的 `GodSystem_UITheme.lua` 常量和 `GodSystem_UI.lua` 渲染函数。
- 网上资源可以提高效率，但必须分授权等级：CC0/公共领域可优先直接用；CC BY 可用但要在 README/Workshop 说明署名；OpenGameArt/itch 等混合授权资源必须逐个查 license；授权不清的只做参考，不进 MOD 包。
- 参考图、商业游戏截图、授权不明的网友素材只能借鉴风格、结构和信息层级，不直接切图打包进 GodSystem。

## v1.16.27 多人分类抽奖与解锁商品本地化经验

- 多人分类抽奖不能只返回“抽奖解锁完成”这种泛提示。玩家需要知道抽中了什么、花了多少、购买价是多少；服务端应在 `result` 回包里带结构化 payload，客户端本地化后弹窗显示。
- `result` 和 `state` 的职责要分开：`result` 携带操作结果并清 pending，`state` 刷新 UI 数据。分类抽奖弹窗应暂存在客户端，等 `state` 到达并刷新列表后再弹，避免结果弹了但列表还没更新。
- 服务端不要把内部物品 ID 当作显示名保存。`unlockAutoShopItem(data, fullType, label, sellValue)` 中 `label` 可以为空；客户端显示已解锁商品时优先用 `GodSystem.getItemDisplayName(fullType)`，只有无法本地化时才使用保存的 label 或 fullType。
- 旧存档可能已经有 `data.unlockedShopItems[fullType].label = "Base.xxx"`。客户端显示层必须兜底修正，不能只修新写入数据，否则老玩家仍然看到英文内部 ID。

## v1.16.28 多人击杀奖励提示经验

- 多人击杀奖励仍使用轻同步设计：客户端累计击杀差值，达到阈值、打开 UI、后台同步或关键操作时同步给服务端，服务端按 `delta * KillPointReward` 发钱。
- 玩家看到的 `+1/+2/+5/+9` 是本次同步批量结算的合计值，不是每只僵尸随机奖励。提示文案必须写成“击杀奖励合计 +N 系统币”这类表达，避免误导。
- 不要为了让提示永远显示 `+1` 而默认改成每杀一只同步一次；这会增加多人模式命令频率、发钱频率和提示噪声，违背当前兼容优先、低压力同步策略。

## v1.16.29 腰包上架与商店分页经验

- 系统腰包不能只判断单一 `fullType`。B42 腰包前戴/后戴会在 `Base.Bag_FannyPackFront` 与 `Base.Bag_FannyPackBack` 间转换，服务器还需要用系统腰包名称做兜底识别。
- 商店长列表不要一次性渲染全部物品。v1.16.29 改为先构建稳定排序后的过滤列表，再按 20 件分页显示；购买/出售前捕获 `selectedFullType` 和滚动位置，重建后按稳定 ID 尽量恢复。
- 分类抽奖不要依赖底部按钮常驻。商店分页占用了底部翻页按钮后，分类抽奖入口应放入分类菜单，避免功能被 UI 布局挤掉。
- 新增腰包“卖掉并上架选中”时，单人走本地回收并解锁，多人走 `recycleWaistAndUnlock` 命令，由服务器验证真实腰包容器、删除物品、发币并写入解锁列表。

## v1.16.44 借贷本地化乱码经验

- GodSystem 的 UI 文本不是只看 `Translate\CN/CH`。运行时经常会优先命中 `GodSystem_Localization_Override.lua` 的 fallback，所以新增中文 key 必须同时检查 Translate 和 Lua fallback。
- `Translate\CN\IG_UI_CN.txt`、`Translate\CH\IG_UI_CH.txt` 的 `IGUI_GodSystem_* = "..."` 表项必须保留行尾逗号。缺逗号可能导致 PZ 翻译表解析异常，最终回落到坏的 fallback 或显示残缺字符。
- `GodSystem_Localization_Override.lua` 中新增中文 fallback 不要直接写中文。为了避免 PowerShell、Lua 文件保存和 PZ 加载路径中的编码差异，优先使用 UTF-8 十进制字节转义，例如 `"\229\128\159\230\172\190"`。
- 不要把 PowerShell 控制台中看到的 mojibake 当作文件已坏，也不要因为控制台显示正常就认为游戏里一定正常。翻译和 fallback 改动后至少跑 `Test-GodSystemEncoding.ps1 -IncludeDocs`，关键新功能再加专项测试检查 key、逗号和 ASCII-only fallback。

## v1.16.46 自动操作与在线理财经验

- SP 与 MP 的自动操作顺序必须保持“腰包自动回收 -> 自动交任务 -> 自动存款”，这样同一小时腰包与任务产生的现金才能被后续存入活期。
- MP 自动操作必须复用现有关键命令 pending 锁，一次只发送一个命令；没有腰包物品、完成任务或随身现金时在客户端推进本次检查基线并静默返回，不发送关键命令。服务端对自动空腰包再做一次无提示兜底，防止库存同步时序造成刷屏。
- 自动开关的起始时间必须保存精确 `getWorldAgeHours()`，不能先 `math.floor()`；否则在整点前开启会在几分钟内误判已经过1游戏小时。
- 自动交任务不能另写奖励逻辑。SP 复用 `GodSystem.claimTask(task, true)`，MP 手动/自动领取共用 `claimTaskForPlayer()`；交物品任务始终由服务端重新扫描并移除真实物品。
- 理财“在线时间”不能用持久化世界时间差直接补算。SP 使用本次 Lua 运行期基线；MP 使用只存在内存的 `investmentOnlineSessions`，玩家对象变化时重置基线，避免离线期间产生结算。
- 服务端 `OnPlayerUpdate` 节流必须按玩家独立计数，不能用一个全局 `_tick`；固定玩家回调顺序下，全局计数可能长期只让某一个玩家进入理财更新。
- 理财账户清空后必须重置在线进度和赎回资格；向非空账户追加投入不能重置计时或已经获得的赎回资格。
- 管理员上涨概率和下跌概率必须限制合计不超过100，下跌概率最多为 `100 - gainChance`，剩余部分自动作为持平概率；客户端显示和服务端结算必须使用同样的清洗规则。
- 概率交叉压缩必须发生在 `sanitizeSettings()` 结果中，而不能只在运行时 profile 中压缩；否则管理员页面会显示80/50，实际却按80/20结算。
- 多人理财提示/历史只传内部档位 ID 和数值，客户端显示层负责把 `stable/balanced/aggressive` 转为本地化名称；不要让服务器发送中文档位名。
- “停止创建新死期”不能只隐藏 UI。SP `createBankFixed*` 和 MP `createFixed*` action 都必须检查 `BankAllowNewFixedDeposits=false` 并拒绝；旧 `bank.fixed` 只保留查询与支取。

## v1.16.48 沙盒、多人理财与精确回收经验

- 原生 `sandbox-options.txt` 只能作为首次默认值。SP 仅在 `data.adminConfig.settings == nil` 时导入，MP 仅在服务端配置存储 `data.settings == nil` 时导入；空表代表已有持久配置，不能再次覆盖。
- 沙盒键必须从 `GodSystem_AdminConfig.lua` 的设置元数据生成并做集合一致性检查，避免手工维护 64 份键后漂移。物品覆盖表是结构化数据，继续留在系统管理页。
- v1.16.46 的服务端 `OnPlayerUpdate` 理财会话计时在多人实测中可能完全不增长。v1.16.48 改为客户端按本次在线会话累计完整世界小时，发送 `syncInvestmentHours`，服务端只接受正整数小时并执行原有 24 小时结算。断线重进重置基线，不补离线时间。
- 原版库存右键多选不能按 `fullType/count` 删除，否则同类型物品可能删错实例。必须展开选中栈、按 `item:getID()` 去重，并在 SP/MP 结算端按 ID 重新查找真实物品。
- 地面、车辆和附近箱子的物品先用 `ISInventoryTransferUtil.newInventoryTransferAction()` 移入玩家库存；转移动作之后追加带完成回调的 `ISWaitWhileGettingUp` 队列屏障，屏障执行并再次验证所有 ID 后才能发送回收请求。不能直接假设最后一个转移动作有 `setOnComplete()`，因为人类尸体会返回 `ISGrabCorpseItem`。转移中断时队列会停止，不能提前发币。
- 右键回收允许收藏、手持、穿戴和普通容器，但必须保护系统币、系统回收腰包、钥匙/钥匙环和隐藏/debug/占位物品。非空容器删除前必须二次确认，收益只算所选外层容器。
- `ItemContainer:Remove(item)` 调用成功不等于物品一定已删除。交易代码必须再检查原容器 `getItems():contains(item)`；物品仍存在时不得发币。失败回滚时还要恢复已解除的主手、副手和穿戴状态。
- 非空容器确认不能只传一个布尔值。确认时要对递归内容实例生成紧凑签名，执行前由 SP/MP 结算端重新计算；内容集合变化时取消整批操作，避免多人共享容器在确认后新放入的物品被误删。
- MP 在线计时基线除了余额清空和世界时间倒退外，还必须在 `OnConnected` 与 `OnDisconnect` 重置。不能假设重连一定会重载整个 Lua 模块。
- `Sandbox.json` 不能在找不到管理页翻译时回落成内部键。专项测试应拒绝 `Sandbox_GodSystem_<Key>` 或 tooltip 的值等于 `<Key>`，确保原生沙盒页保持中文可识别。
- 服务端大型单文件可能接近 Lua 5.1 的 200 个顶层局部变量上限。新增一次性 helper 前必须跑 `luac -p`；必要时复用现有 helper、内联单次逻辑或使用明确命名的模块函数，不能等进游戏才发现编译失败。
## v1.16.50 B42.19 纯渲染同伴经验

- 仅限单人的系统必须在运行时文件第一行使用 `(isClient and isClient()) or (isServer and isServer())` 直接返回。主 UI 也只在 SP 条件下 `require` 运行时和快捷栏；共享数值配置可以被双方读取，但不能注册事件。
- v1.16.49 实机证明：`IsoZombie` 外壳即使设置无牙、无用、无目标、无仇恨和无碰撞，仍可能咬人、制造恐慌/压力、被击倒后不起身。无害视觉同伴不得再复用僵尸实体架构。
- 纯视觉同伴保存逻辑世界坐标，通过 `OnPreUIDraw` 绘制贴图；候选点检查同层、实体格、可见区域和固体标志，不创建世界对象。
- 旧存档只保留一次 `GodSystemProjection` 标记外壳清理。运行时不得再调用 `addZombiesInOutfit()`、`ItemVisual`、外貌复制或形态切换。
- `IsoLightSource.new(x,y,z,r,g,b,radius)` 配合 `cell:addLamppost()` 可创建动态光源。只在跨格、半径改变、显隐和清理时重建，并保存创建时的 cell 供 `removeLamppost()` 使用。
- B42.19 屏幕特效可参考 Bandits/Sentry Turret：`ISCoordConversion.ToScreen()` 后除以当前 zoom，再使用 `getRenderer():renderline(mask_white, ...)`。仅在 `OnPreUIDraw` 绘制当前短生命周期弹道和标记。
- 致死伤害应先 `setAttackedBy(player)`，扣血后调用 `Kill(player)` 进入原版死亡路径，再比较击杀数并只在未增长时补到旧值加一，避免任务和击杀奖励漏计或重复。
- 页面重建后必须用稳定节点 ID 恢复选择，例如 `companionNode:<nodeId>`；不能在购买升级后把玩家弹回列表开头。
- B42.19 Kahlua 环境不能假设标准 Lua `math.random()` 存在。连续浮点随机使用本体已验证的 `ZombRandFloat(min,max)`；整数范围使用 `ZombRand(min,max)`，新增随机逻辑必须先检索本体同版本调用。
- B42.19 能通过 `getTexture()` 成功取得 `Texture`，不代表 `getRenderer():render(texture,x,y,w,h,r,g,b,a)` 存在可由 Kahlua 调用的 Java 重载。实机报错为 `No implementation found for function: render(... Double ...)`。GodSystem 浮游机器人因此改为内置 `mask_white.png + renderline()` 直接绘制，避免继续猜测 `SpriteRenderer.render` 参数类型。

## v1.16.53 B42 属性、车辆与服务端编译边界

- 动态技能枚举可用 `Perks.getMaxIndex()` 和 `Perks.fromIndex()`，但 B42.19 原版界面把 `PerkFactory.getPerk(perk)` 返回值作为技能元数据对象。名称、父类和 `getTotalXpForLevel(level)` 应优先从该对象读取，枚举值只作为 XP API 的 perk 参数和兼容回退。
- MP 技能经验不能信任客户端报价。客户端只提交 perk index、购买模式和输入值；服务端重新解析技能、XP 曲线和价格，按活期后现金扣费。B42.19 原版管理界面已验证无倍率写法为 `player:getXp():AddXP(perk, amount, false, false, false, false)`；调用后必须读取实际 XP 差额，再调用 `SyncXp(player)`。
- 属性购买需要按玩家连接与 `opId` 做有界幂等缓存；客户端只有在同一条超时请求的技能、模式和输入完全一致时才复用旧 `opId`。失败退款必须保留 `fromBank/fromCash`，实体币返还失败时把等值金额转入活期，不能让退款再次造成损失。`SyncXp` 在 XP 已生效后失败时不能退款，否则会产生免费 XP；应记录待同步状态并在重连时重试。
- B42.19 原版车辆整车修复入口 `ISVehicleMechanics.onCheatRepair()` 发送 vehicle ID，服务器最终使用 `vehicle:repair()`。MOD 服务端可用 `getVehicleById()` 定位，但仍要验证真实耗材、同层、距离或乘坐关系。
- `GodSystem_Server.lua` 在 v1.16.52 已有 200 个顶层 local 声明。本轮新增五个顶层 helper 后，Lua 5.1 `luac` 报 `main function has more than 200 local variables`。最终将 helper 挂到已有 `GodSystemServer` 表后恢复通过。以后不要继续在该文件增加顶层 local；优先使用命名空间方法或独立模块。
- 同伴副伤害必须走统一的 `applyCompanionDamage()`，并由直击函数单独触发附加效果。灼蚀、连锁、爆裂不得再次调用直击特效入口，否则会递归扩散和重复结算击杀。

## v1.16.54 可穿戴容器、容量上限与未发布版本

- B42.19 自定义可穿戴容器不能只写 `CanBeEquipped`。物品脚本必须同时写同值的 `BodyLocation`，并由 `media/registries.lua` 调用 `ItemBodyLocation.register()`；否则右键穿戴提示会在 `BodyLocationGroup.isExclusive()` 报 `first is null`，实际穿戴会在 `isMultiItem()` 报 `location is null`。
- B42.19 `ItemContainer.setCapacity()` 会拒绝超过 50 的值并持续写警告。GodSystem 将终端上限固定为 49；不要用 `pcall` 把引擎警告误当成设置成功。
- 分类标题、解释、汇总和空状态应通过统一 `selectable=false` 规则处理。绘制层也必须只给可操作行画 `rowSelect`，否则即使动作层忽略点击，视觉上仍像被选中。
- 短时战斗特效应在触发时保存世界坐标。只保存僵尸对象会在目标死亡或失效后让特效提前消失。
- 未发布测试版本不建立兼容负担。只有用户明确确认版本已经发布，下一版才迁移该发布版的物品和字段；测试确认前不推送 GitHub。

## v1.16.55 实机穿戴、选择恢复与车辆修复经验

- 自定义穿戴槽即使同时注册 `ItemBodyLocation`、`BodyLocation` 和 `CanBeEquipped`，仍必须以目标 B42 小版本实机穿戴为准。v1.16.54 的独立槽定义完整后仍失败，因此当前终端改用已验证的原版 `base:necklace`，并删除未发布自定义槽，不再把“静态字段齐全”等同于“运行时可穿戴”。
- 列表操作不能只在 `populateList()` 开头捕获当前选择。MP 等待 state 时列表可能已被同步占位行清空，下一次捕获会把有效 ID 覆盖成空值。购买前应保存一次性 `pendingRestoreSelectedId`、页面和滚动位置；真实列表重建并成功命中稳定 ID 后再清除。
- 同伴视觉位置与能力运行位置应解耦。逻辑移动只验证同层、已加载和非实体阻挡；可见位置只作为优先目标。进入玩家不可见格时暂停绘制本体，但不能停止移动、照明或战斗，也不能仅因不可见强制召回。
- 自定义消耗品必须进入显式价格表；仅放进工具分类会落入分类兜底价。车辆修复模块的 220 就来自该兜底，修复方式是显式配置 `GodSystem.SystemVehicleRepairModule = 5000`。
- B42.19 整车修复应统一在服务端边界执行。SP 也通过独立 server Lua 监听现有 `useMaintenanceItem` 命令，验证真实模块、车辆、楼层和距离后调用共享 `GodSystemMaintenance.repairVehicle()`；客户端只负责确认和展示结构化结果。修复后按部件发送 condition、item、ModData，并刷新部件、弹道和损伤外观统计。
- B42.19 原版 `ISModalDialog:new(..., target, onclick, player, param1, param2)` 点击后调用的是 `onclick(target, button, param1, param2)`。`player` 只写入 `button.player`，不会插入回调位置参数。车辆 payload 放在 `param1` 时，正确签名是 `Context.onConfirm(target, button, payload)`；多写一个 `playerNum` 会让 payload 变成 `nil`，被前置保护静默返回。
- “弹窗正常出现”只证明弹窗创建成功，不证明确认回调、客户端发送或服务端处理已经运行。排查无消耗、无效果问题时，应分别记录确认回调入口、客户端发送、SP/MP 服务端接收、验证、实际修改和结果返回；同时比较 `console.txt` 与部署文件时间，避免拿旧会话日志判断新诊断代码。

## v1.16.63 空间减载经验

- B42.19 的 Java 容量检查不会保证经过 Lua 替换的 `ItemContainer` 暴露方法；v1.16.62 包装 `getEffectiveCapacity()` / `hasRoomFor()` 后 UI 可显示大容量，但真实放入仍可能失败。不能把 Lua 方法覆盖当作 Java 内部调用钩子。
- 普通 `InventoryItem:setActualWeight()` 会夹紧负数；Food 的实例 `hungChange` 会进入原版存档，并可通过原生实际重量公式产生负值。对目标减载 `R` 使用 `hungChange=R/100` 后必须读取 `getActualWeight()` 验证约等于 `-R`。
- 隐藏内部物品不能只依赖 `Hidden=true`。批量转移仍可能遍历真实容器，因此还要设置 favorite/unwanted，并在回收、上架、抽奖和终端统计中按 fullType 明确排除。
- 保护不需要每帧轮询。领取、找回、终端查找、页面打开、升级、自动回收、读档、MP握手和显式刷新已经覆盖主要边界；多人创建/删除内部物品后必须同步容器变化。
- `GodSystem_Server.lua` 已接近 Lua 5.1 的200个顶层 local上限。本版新增同步 helper 必须挂到 `GodSystemServer` 命名空间；仅通过静态文本测试无法发现该限制，必须运行正式 `luac -p`。
