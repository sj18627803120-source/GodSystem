## 右键卡顿候选

### 1. 世界右键先递归查背包，后判断车辆

- 入口：`client/GodSystem_VehicleRepairContext.lua:83`，`Context.fillWorldMenu()`。
- `test` 检测调用会直接返回；正常菜单调用先在第 86 行执行 `findModule(player)`，然后才在第 88 行调用 `selectedVehicle(player)`。
- `findModule()`（第 16 行）使用 `inventory:getFirstTypeRecurse(ModuleType)` 查找修车模块。
- 因此普通地面右键也会进入递归背包查询。未携带模块、或模块在搜索顺序末尾时，可能遍历整个携带库存及嵌套容器。
- 合理推断：背包物品很多时，这是世界右键延迟的优先排查点；开销随库存规模增长。命中车辆且携带模块时，还会同步遍历车辆零件生成损坏摘要。
- 最小优化方向：先判断车辆，再查消耗品；最终确认时仍重新查找真实消耗品。具体耗时应在目标 B42.20 环境采样确认。

### 2. 库存右键重建完整范围回收名单

- 入口：`client/GodSystem_RecycleContext.lua:452`，`Context.fillInventoryMenu()`。
- 第 478 行无条件准备范围名单菜单；`rangeFilterPayload()`（第 260 行）取视图后调用 `GodSystemRangeFilter.normalize(state.filter)`，随后遍历名单重建 `active` 查询表。
- `shared/GodSystem_RangeFilter.lua:26` 的 `cleanBatch()` 会遍历、校验、去重和排序全部名单；第 52 行的 `normalize()` 每次重新调用它。名单上限为 20,000 种。
- 没有按名单 `revision` 缓存该结果，即使只右键一件物品，也付出完整名单的清洗、排序及建表成本。此处也没有根据 `state.enabled` 提前跳过；仅关闭范围回收功能不能保证绕过这个开销。
- `client/GodSystem_RangeRecycleService.lua:29` 的 `stateFor()` 首次未加载名单时会读取本地文件；读取失败且 `filterLoaded` 未置位时，后续取视图还会重试。正常成功加载后不会每次读文件，但上面的清洗排序仍重复发生。
- 合理推断：大名单用户的普通库存右键延迟，应优先检查此路径；文件加载只作为首次打开或持续加载失败的附加风险。
- 最小优化方向：用名单 revision 缓存成员集合；在加载或名单变更边界归一化，菜单只查询缓存；功能关闭时尽早跳过相应菜单构建。

### 3. 大堆叠/多选仍逐件展开和分类

- `client/GodSystem_InventoryContext.lua:69` 的 `expand()` 展开所选堆叠；第 39 行的 `append()` 为每个真实物品读取 ID、类型、家具 sprite 和功能标记。
- 第 121 行的分发器同步调用所有已注册处理器；回收处理器再执行 `createAnalysisCache()`、`classifyAll()` 和所选类型收集。
- 现有代码已经共享一次选择快照，并按 fullType/variantKey 复用部分检查，不能将其描述为“每个模块都重新扫描全部库存”。但物品实例展开、建表、分类仍随选择数量线性增长，没有分帧或延后计算。
- 合理推断：单件正常、右键大堆叠或全选才卡时，此路径更符合症状；大量临时表和跨 Lua/Java 方法调用可能放大开销。

### 4. 点击批量回收后的重复全背包查找（区别于弹出菜单）

- `client/GodSystem_RecycleContext.lua:357` 的 `Context.execute()` 对每个选中 ID 调用递归 `containsId()`。
- SP 继续进入 `client/GodSystem_ClientRuntime_Recycle.lua:319`，循环对每个 ID 调用 `gsInventoryItemById()`。
- `client/GodSystem_ClientRuntime_Foundation.lua:238` 的 `gsInventoryItemById()` 每次先通过 `gsFindInventoryItems(nil, true, true)` 收集完整库存，再寻找目标 ID。
- 因而批量操作至少存在“所选数量 × 库存规模”的查询成本。它发生在选择回收操作、必要确认和转移之后，不能用来解释单纯打开右键菜单的延迟。
- 最小优化方向：同一事务构建一次真实 ID 索引，并在实际删除/结算边界保留实例存在性与所属容器复验。

## 商城最多五页：当前代码不支持这个上限判断

已沿上架、保存、投影、接收、过滤、分页和按钮调用链核对，未发现固定五页或 100 条商品的截断。

| 环节 | 当前代码行为 |
| --- | --- |
| SP 上架 | `client/GodSystem_ClientRuntime_Economy.lua:520` 按 variantKey 写入 `data.unlockedShopItems`，无总条数上限 |
| MP 上架 | `server/GodSystem_ServerRuntime_EconomyTasks.lua:395` 按 variantKey 写入，同样无总条数上限 |
| 列表整理 | `shared/GodSystem_ShopVariants.lua:117` 遍历全部记录，过滤 hidden / disabled / forced，未按数量截断 |
| 客户端列表 | `client/GodSystem_ClientRuntime_Economy.lua:622` 遍历上述全部记录，检查物品定义存在性并排序 |
| MP 投影 | `shared/GodSystem_StateProjection.lua:125` 的 `copyUnlocked()` 复制全部有效物品记录；深度保护不是商品条数限制 |
| MP 发送/接收 | `server/GodSystem_ServerRuntime_RouterConfig.lua:37` 发送状态，`client/GodSystem_Network.lua:781` 接收并替换显示数据，未做 100 条切片 |
| 分页 | `client/GodSystem_UI_Runtime_Pages.lua:70` 使用 `ceil(#filteredShopItems / pageSize)`；`ShopPageSize = 20` |
| 下一页 | `client/GodSystem_UI_Runtime_Actions.lua:521` → `changeShopPage(1)`；`client/GodSystem_UI_Runtime_Lists.lua:691` 递增页码，随后只按实际总页数夹取 |

按当前公式，81–100 条可见商品为 5 页，101 条为 6 页，121 条为 7 页。这是代码公式推导，不是实机测试结果。页眉数量包含合并后的内置、玩家上架和管理员强制商品，不等同于背包里的物品实例数量。

玩家看不到新增商品时，应按下列数据边界核对：

1. 上架是否确实成功：开关、黑名单、允许模块、重复商品身份以及付款/真实物品校验都可能阻止新增记录。
2. 是否重复上架同一商品：普通物品以 fullType 为身份，家具以 fullType + worldSprite 为身份；重复实例不会增加商城条目。
3. 当前分类和搜索是否过滤了新增条目；隐藏商品、管理员 disabled 配置、已不存在的物品定义也会减少可见数量。forced 商品从另一列表合并，不能只查玩家上架列表。
4. MP 中服务端和客户端的真实记录数量是否一致。虽然 MOD Lua 未写五页限制，但大状态包仍整体发送；实际丢包、序列化失败、客户端旧状态或加载了不同版本需要日志与存档证明，当前不能确定。

如果页眉已经显示超过 100 条且总页数仍是 5，或显示超过 5 页但无法翻到第 6 页，应记录界面、页眉、实际加载版本和日志；这与当前分页公式不符，需要复现环境进一步定位。
