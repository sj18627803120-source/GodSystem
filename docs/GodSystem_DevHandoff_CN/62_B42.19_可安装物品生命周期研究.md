结论分级：

- **高**：本机 B42.19 原版 Lua、脚本或本机游戏 JAR 直接确认。
- **中**：原版调用链基本完整，但仍缺少一次目标环境实机或 MP 验证。

## 2. 结论摘要

1. 当前 v1.16.66 的首个确定失败点不是 `IsoCarBatteryCharger.new()`，而是客户端加载 `GodSystem_StorageContext.lua` 时无法加载 `BuildingObjects/ISBuildingObject`，随后在第 24 行对 `nil` 调用 `derive`。证据为 `C:\Users\Admin\Zomboid\console.txt:5391-5403`。置信度：**高**。
2. `skipBuildAction` 只决定是否跳过 `ISBuildAction`；`dragNilAfterPlace` 只控制光标清理；`canBeAlwaysPlaced` 只放宽基础格子检查。三者都不能代替有效的类加载、鼠标释放状态、`isValid()`、世界对象创建或 MP 同步。置信度：**高**。
3. B42.19 最完整、最接近“背包物品放置为世界对象，再拾回背包”的原版通用生命周期是 Moveable 系统。它负责格子验证、行走、Timed Action、按世界贴图创建对象、物品移除、对象同步和拾取。置信度：**高**。
4. Moveable 拾取通常创建新的 `InventoryItem`，不保留原物品 ID。控制器网络身份不能继续依赖物品 ID，应该使用独立网络 ID、令牌和 `movableData`。置信度：**高**。
5. 电池充电器会把原 `InventoryItem` 保存在 `IsoCarBatteryCharger` 内并在拆卸时取回，理论上保留同一物品实例；但世界对象始终是充电器，会进入充电器专用右键、充电和电池逻辑，因此不适合作为通用仓库控制器。置信度：**高**。
6. 发电机不是原物品实例往返：原版 Moveable 世界贴图分支会新建发电机内部物品，`ISTakeGenerator` 拾回时也重新创建 `Base.Generator` 或 `generatorFullType`。置信度：**高**。
7. 推荐下一轮先做独立的 Moveable 最小实验，不直接修 GodSystem 控制器。只有验证自定义 `CustomItem`、`movableData`、存档重载和 MP 往返后，才进入正式实现。置信度：**中高**。

## 5. Moveable 家具

### 5.1 背包物品和世界贴图

- `C:\APP\Steam\steamapps\common\ProjectZomboid\media\scripts\generated\items\moveable.txt:1-80` 展示标准 `ItemType = base:moveable` 定义。
- `ISMoveableSpriteProps:instanceItem():205-231`
  - 有贴图 `CustomItem` 时创建指定物品。
  - 没有 `CustomItem` 时创建 `Moveables.Moveable` 或 `Moveables.<spriteName>`。
  - `ReadFromWorldSprite(spriteName)` 把世界贴图写入 Moveable 物品。
- 同一 `fullType` 的不同家具主要依靠 `item:getWorldSprite()` 区分，不应只按 `fullType` 识别。

最终控制器如果采用 Moveable，必须确认：

1. 自定义世界贴图具有 `IsMoveAble`。
2. 贴图 `CustomItem` 指向 GodSystem 控制器物品。
3. 物品 `WorldObjectSprite` 与贴图一致。
4. 拾回后仍创建 GodSystem 控制器，而不是通用 `Moveables.*` 或其他原版物品。

这些条件尚未通过最小实机实验。置信度：**中**。

这条路径比 GodSystem 当前“自定义光标直接调用客户端服务”更完整。置信度：**高**。

### 5.3 世界对象类型

`ISMoveableSpriteProps:placeMoveableInternal():1929-2406` 根据世界贴图和属性决定 Java 世界对象：

因此 `base:moveable` 不是“指定任意 Java 对象类型”的接口；真正类型由世界贴图属性决定。置信度：**高**。

### 5.4 拾取、ID 和 ModData

`ISMoveableSpriteProps:pickUpMoveableInternal():1269-1412`：

- 第 1272 行调用 `instanceItem()` 创建新物品。
- 第 1318-1320 行把新物品加入库存并同步。
- 第 1401-1403 行移除原世界对象。

因此拾回物品通常是新实例，物品 ID 会变化。置信度：**高**。

状态转移：

- `saveThumpableParameters():1199-1226` 把 Thumpable 名称、生命、颜色、锁、灯光和完整对象 ModData 保存到物品 ModData。

冰箱、冰柜等多容器家具不是把容器内物品一起打包进一个 Moveable；它们先要求为空，再由世界贴图和组件重新创建容器结构。置信度：**高**。

所以右键菜单能出现或部分逻辑能运行，不代表放置类、`DoTileBuilding()` 或服务端安装事务已经可用。置信度：**高**。

### 8.2 B42.19 `DoTileBuilding` 的实际要求

必须同时满足：

1. drag 对象已被 `getCell():setDrag()` 注册。
2. `player` 字段存在。
3. 鼠标按下和释放状态完成，且点击没有被 UI 消费。
4. 渲染阶段 `isValid()` 返回真并写入 `canBeBuild`。
5. 释放时 `build` 变为真。
6. `DoTileBuilding()` 调用 `tryBuild()`。
7. `tryBuild()` 能行走或满足特殊条件。
8. `create()` 或 Timed Action 最终创建对象。

任何一个环节未发生，都可能没有红字但没有安装结果。置信度：**高**。

### 8.3 三个标志是否足够

- `skipBuildAction`：不够。只跳过 `ISBuildAction`。
- `dragNilAfterPlace`：不够。只影响放置后光标清理。
- `canBeAlwaysPlaced`：不够。只放宽 `ISBuildingObject:isValid()` 的基础格子限制，不能绕过自定义 `isValid()`、鼠标状态、类加载、创建和同步。

结论：三者不能修复当前失败。置信度：**高**。

### 8.4 当前 `tryBuild/create` 是否符合约定

静态形状上：

- `ControllerPlacement:tryBuild(x,y,z)` 能接收原版调用参数。
- 它重新取 square、调用自定义 `isValid()`，再调用 `create()`。
- `create(x,y,z)` 清 drag 并调用客户端服务。

问题在于：

1. 类没有成功加载，约定没有机会执行。
2. 覆盖 `tryBuild()` 后完全绕过原版 `ISBuildingObject:tryBuild()` 的行走、Timed Action 和建造事务。
3. MP 同步完全依赖后续自定义命令，不再得到原版建造事务保护。

因此只能判断“函数签名表面匹配”，不能判断“生命周期符合 B42.19”。置信度：**高**。

### 8.5 `IsoCarBatteryCharger.new(customItem,...)` 是否允许普通物品

Java 构造器接受任意非空 `InventoryItem`，并保存/加载该物品；GodSystem 普通控制器在参数类型上没有被排除。置信度：**高**。

但正式适用性仍为否：

- 世界对象类型固定为 `IsoCarBatteryCharger`。
- 右键和内部状态固定为充电器。
- 自定义物品的世界图形、存档后模型、充电器操作和 MP 行为未验证。

结论：**构造器可接受不等于架构可复用**。

### 8.6 当前对象应该在哪一侧创建

- SP：当前 `Client.installController():217-241` 在非 MP 时直接调用 `Manager.installController()`。这条路径是否运行在可持久化的 SP 服务端上下文，需要最小实机验证。
- MP：`Client.installController():223-236` 发送 `installController` 命令；`GodSystem_StorageServer.Commands.installController():204-209` 在服务端调用 Manager。该方向符合服务端权威要求。
- 官方 B42 Inventory Items 指南也要求 MP 的物品创建、删除和修改由服务端执行，并显式同步；仓库内摘要见 `docs/PZ_B42_OFFICIAL_DEVELOPMENT_CN.md:14-24`。

结论：MP 世界对象创建必须由服务端执行；SP 应使用经 B42.19 验证的本地服务端/Timed Action complete 路径，而不是只凭 `isClient()` 推断。置信度：**高**。

## 9. 推荐方案

### 第一名：真正的 Moveable 控制器

建议把控制器设计为 B42.19 标准 Moveable，而不是自定义 `ISBuildingObject` 光标或伪装充电器。

最小架构：

1. 控制器物品使用 `ItemType = base:moveable`。
2. 使用专用世界贴图，贴图具有 `IsMoveAble`、正确 `MoveType` 和 `CustomItem = GodSystem.SystemStorageController`。
3. 网络身份和令牌保存到 `item:getModData().movableData`。
4. 世界对象右键只读取 `object:getModData().movableData`。
5. 放置、拾取和格子验证复用 `ISMoveableCursor`、`ISMoveablesAction`、`ISMoveableSpriteProps`。
6. 不依赖物品 ID；拾回后允许新 ID，但网络 ID 和令牌必须不变。
7. GodSystem 服务端继续验证控制器唯一性、权限和网络状态，不信任客户端 ModData。

优点：

- 使用当前版本原版完整生命周期。
- 原版已处理行走、空容器、格子、贴图、对象创建、拾取和对象同步。
- 帐篷已证明 B42.19 将便携设备放在 Moveable 路线。

风险：

- 必须验证自定义贴图注册和 `CustomItem`。
- 原物品 ID 会变化。
- 原版 Moveable 的 MP 权限和 GodSystem 唯一性仍需额外服务端校验。

置信度：**中高**。

### 备选：标准格子选择 + 服务端自建 `IsoThumpable`

如果自定义 Moveable 贴图无法稳定注册，可使用一个已验证可加载的标准格子选择器，只传坐标；服务端重新验证玩家、物品、距离、楼层和占用后创建普通 `IsoThumpable`，写入 ModData 并同步。收回时由服务端移除对象、重新创建控制器物品并恢复身份数据。

要求：

- 不保留原物品 ID。
- 明确定义先创建还是先移除以及失败回滚顺序。
- 不再使用 `IsoCarBatteryCharger`。
- SP 和 MP 共用服务端权威创建函数。

优点：对象语义干净，可完全控制右键和 ModData。

风险：需要自己维护放置、回滚、重复请求、存档和同步，测试面比 Moveable 大。

置信度：**中**。

## 10. 明确排除的方案

### 10.1 继续直接 require 客户端 `ISBuildingObject`

排除原因：本机 B42.19 已实际加载失败，日志证据完整。置信度：**高**。

### 10.2 依赖 `skipBuildAction=true` 作为 MP 安装协议

排除原因：它明确绕过 `ISBuildAction` 和 `createBuildAction`，不提供服务端事务。置信度：**高**。

### 10.3 把 `IsoCarBatteryCharger` 当通用控制器

排除原因：虽然构造器接受普通 `InventoryItem`，但对象语义、右键和内部逻辑固定为充电器。置信度：**高**。

### 10.4 营火或普通建造物材料路线

排除原因：它们以材料创建对象、拆除返还材料，不保留完整控制器状态。置信度：**高**。

### 10.5 继续使用普通地面世界物品

排除原因：GodSystem 先前实机已确认普通地面物品右键入口不稳定；本轮参考 MOD 的 `AddWorldInventoryItem()` 也只证明掉落同步，不证明安装设备生命周期。置信度：**中高**。

## 11. 下一轮最小实机实验

不要直接改正式控制器。新建一次性实验 MOD 或测试物品，步骤如下：

1. 创建一个 `base:moveable` 测试物品和一个专用可移动世界贴图。
2. 贴图 `CustomItem` 指向测试物品。
3. 在物品 `modData.movableData` 写入固定 `networkId`、`token` 和测试值。
4. SP 放置前记录：
   - fullType
   - item ID
   - worldSprite
   - movableData
5. 放置后记录：
   - 世界对象 Java 类型
   - 对象 index
   - 对象 movableData
6. 保存退出、重进，复查对象类型和 movableData。
7. 拾回后记录新物品 fullType、ID、worldSprite 和 movableData。
8. 确认 ID 可以变化，但 fullType、网络 ID、令牌和状态不变。
9. MP 由主机和远程玩家分别执行一次放置/拾回。
10. MP 重登后复查对象；两名玩家同时拾取时只允许一方成功。

通过标准：

- 无红字。
- 不产生普通地面物品残留。
- 放置和拾回不复制、不丢失。
- 自定义 fullType 正确往返。
- movableData 跨保存、拾回和 MP 同步。

若第 1-8 步失败，停止 Moveable 正式实现，转备选服务端 `IsoThumpable` 实验。

## 12. SP 已确认与 MP 必测边界

### SP 已能从代码和现有日志确认

- 当前失败发生在 `ISBuildingObject` require/derive 阶段。
- `DoTileBuilding` 的鼠标、验证和 `tryBuild` 条件。
- `skipBuildAction`、`dragNilAfterPlace`、`canBeAlwaysPlaced` 的真实作用。
- 原版建造物创建 `IsoThumpable` 并消耗材料。
- Moveable 创建新拾回物品，不保留原 ID。
- Moveable 可转移 `movableData`、Thumpable ModData、组件和容器名称。
- 电池充电器保存原 `InventoryItem`。
- 发电机拾回时新建物品。
- 营火拆除返还石头。

### 必须通过 SP 实机继续确认

- 自定义 Moveable 贴图和 `CustomItem` 是否正确注册。

- 自定义 movableData 是否跨保存重载。
- 发电机首次放置的实际入口。

- 服务端重启后对象 ModData 和网络索引是否一致。

## 13. 最终建议

下一轮不要继续修补当前 `ControllerPlacement`。先用最小 Moveable 实验验证“自定义物品 -> 世界对象 -> 保存重载 -> 新物品”的完整往返。实验通过后，正式控制器采用独立网络身份而不是 item ID，并把全部可迁移状态放入 `movableData`。如果自定义 `CustomItem` 或 MP 往返失败，再实施服务端权威 `IsoThumpable` 方案。
