# v1.16.34 抽奖奖池过滤与分类参考方案

## 背景

玩家反馈独立抽奖页的奖池里出现了明显不该给玩家的内部物品，例如 `zed_dmg_facehit` 一类动画/伤痕/隐藏道具，并建议参考 `CAExtendedCategories` 的分类识别逻辑。

本次只做分析和技术文档沉淀，尚未修改实时 MOD 功能代码。当前实时目录仍是 v1.16.33，因此这个问题在当前版本仍有可能出现。

相关目录：

```text
实时 MOD：C:\Users\Admin\Zomboid\Workshop\GodSystem
参考 MOD：C:\Users\Admin\Desktop\PJ\File\CAExtendedCategories
游戏本体：C:\APP\Steam\steamapps\common\ProjectZomboid
```

## 结论

问题成立。GodSystem 当前抽奖候选池只判断物品脚本是否存在，没有判断物品是否隐藏、废弃、调试、内部用途或非玩家可见。

`Base.ZedDmg_*`、`Base.Test*`、`Base.Animal_Item_Dummy` 这类物品已经进入 `GodSystem_Prices.lua` 的价格表和分类表，抽奖候选池又会从 `VanillaItemBuyPrices` 全量吸入，因此会被抽到。

下一版应先增加“抽奖优先的经济候选可用性过滤层”，再让抽奖、商店展示、回收/上架候选池按需调用。v1.16.34 的最低目标是先堵住抽奖奖池；如果要宣称经济系统全局修复，则还必须同步接入商店、管理页和价格表生成流程。

抽奖必须在客户端预览和服务端实际发放两边都过滤，多人模式最终以服务端奖池为准。

## CAExtendedCategories 参考结论

参考路径：

```text
C:\Users\Admin\Desktop\PJ\File\CAExtendedCategories
```

关键文件：

```text
common\media\lua\shared\CAExtendedCategories\CAEC.lua
common\media\lua\shared\CAExtendedCategories\CAEC_Utils.lua
common\media\lua\shared\CAExtendedCategories\Categorizers\CAEC_Apparel.lua
```

已确认机制：

- `CAEC.CategorizeAllItems()` 扫描 `getAllItems()` 后调用 `CAEC.CategorizeItem(item)`。
- `CAEC.CategorizeItem()` 会查静态覆盖、缓存、实例专用分类，再调用分类器。
- `Utils.HasAnyTag(item, tags)` 使用 `item:getTags()` 和 `item:hasTag(tag)` 判断标签。
- `Utils.CreateInstanceIfNeeded()` 会调用 `instanceItem(item)` 创建临时实例，并缓存。
- `CAEC_Apparel.lua` 的服装验证明确排除：
  - `ItemBodyLocation.WOUND`
  - `ItemBodyLocation.ZED_DMG`
  - `ItemBodyLocation.BANDAGE`

对 GodSystem 的可借鉴点：

- 分类不能只靠 GodSystem 自己生成的价格分类表。
- `Tag`、`BodyLocation`、`DisplayCategory`、`ItemType` 都可以作为辅助判断。
- `ZED_DMG`、`WOUND`、`BANDAGE` 这类 body location 不应该进入普通装备/服装/抽奖池。

不建议直接照搬的点：

- 不建议在抽奖候选池里完整运行 CAEC 的实例化分类流程。
- `instanceItem(item)` 对大型奖池可能有额外开销，也可能对某些 mod 物品触发警告或失败。
- GodSystem 当前目标是稳定排除内部/隐藏物品，不是替代 CAEC 做全量分类系统。

## 建议设计

新增一个“经济候选可用性”判断，建议命名方向：

```lua
GodSystem.isEconomicItemAllowed(fullType, context)
```

优先放在 `shared` 侧，由客户端和服务端共同调用。不要默认在客户端/服务端各写一份同名本地 helper；如果受加载顺序限制必须镜像实现，必须追加静态测试确认两边规则一致，避免 MP 预览池和服务端发放池漂移。

建议过滤顺序：

1. `fullType` 非空。
2. 使用 `getScriptManager():FindItem(fullType)` 取得 `scriptItem`；抽奖上下文中如果 `getScriptManager` 不可用或 `scriptItem` 不存在，直接排除，不沿用现有 `itemExists()` 的失败放行行为。
3. 所有脚本物品 API 调用都用 `pcall` 包住，避免异常物品让整个奖池构建中断；抽奖上下文中核心字段读取失败时按“不允许进入奖池”处理，不回退放行。
4. 用 `pcall` 调用 `scriptItem:getObsolete()`；调用失败或返回真，排除。
5. 用 `pcall` 调用 `scriptItem:isHidden()`；调用失败或返回真，排除。
6. 读取可用字段做轻量补充过滤：
   - `DisplayCategory` 等于或归一化后等于 `ZedDmg`，排除。
   - `BodyLocation` 只从脚本物品的 body location API 判断；优先使用 `scriptItem:isBodyLocation(ItemBodyLocation.ZED_DMG/WOUND/BANDAGE)`，退而求其次再归一化 `getBodyLocation()` 的返回值。不要匹配 `fullType`、显示名或普通分类里的 `bandage`，否则会误伤真实医疗物品 `Base.Bandage`。
7. 精准兜底黑名单模式：
   - `Base.ZedDmg_`
   - `Base.TestHotDrink`
   - `Base.TestMug`
   - `Base.TestWaterMug`
   - `Base.Animal_Item_Dummy`
8. 可选的保守内部词匹配只用于官方 `Base.*`，例如：
   - `_Dummy`
   - `Debug`
   - `Hidden`
   - `Placeholder`
   - `Template`
   - `Unused`

不要全局排除所有名字包含 `Test` 的 mod 物品。社区 mod 可能有真实物品名称包含 test，误杀会影响兼容性。官方字段 `isHidden` / `getObsolete` 应该永远优先。

## 应用范围

下一版最低必须接入：

- 客户端 `gsLotteryAddCandidate()`。
- 服务端 `lotteryAddCandidate()`。
- 客户端旧兼容路径 `GodSystem.getShopLotteryCandidates()`，防止未来旧入口或管理页复用时漏过滤。

服务端 `Commands.shopLottery()` 当前已经转发到 `Commands.lotteryDraw()`，因此服务端旧命令不需要单独维护一套候选池，但仍要通过 `lotteryDraw()` 使用同一过滤规则。

建议后续继续评估：

- 商店自动解锁候选池。
- 管理页物品覆盖列表。
- 回收/上架的全局候选来源。

注意：玩家背包里真实存在的物品不应该被过度拦截。回收/出售场景可以先只排除 `hidden/obsolete` 和明确内部物品，避免玩家因为某些 mod 特殊物品无法正常卖出。

## 多人模式要求

- 客户端预览过滤只是为了 UI 显示干净。
- 服务端实际抽奖必须再次过滤，服务端奖池才是最终结果。
- 如果客户端显示的候选数和服务端不同，以服务端返回为准。
- 多人抽奖结果弹窗仍由服务端返回的结果驱动，不由客户端自行生成最终结果。

## 管理配置关系

当前 `GodSystemAdminConfig.isLotteryItemEnabled(fullType, true)` 只能表达“管理员是否允许该物品参与抽奖”。

建议规则：

- 管理员禁用某物品时，必定排除。
- 管理员启用某物品时，也不能绕过 `hidden/obsolete` 基础过滤。
- 管理员普通启用开关只表示“允许候选源中的普通物品参与抽奖”，不应新增候选源，也不应强行允许隐藏/废弃物品。
- 如果未来确实需要强行允许隐藏物品，需要新增明确的 `forceLotteryHiddenItems` 或单物品 `force=1` 配置，不要复用普通启用开关。

这样能避免服主无意间把内部物品重新放回奖池。

## 测试清单

下一版实现时建议先写静态/脚本测试，再改 Lua。

必须排除：

- `Base.ZedDmg_BACK_Slash`
- `Base.ZedDmg_BulletFace01`
- `Base.TestHotDrink`
- `Base.TestMug`
- `Base.TestWaterMug`
- `Base.Animal_Item_Dummy`
- `Base.Bandage_LeftUpperArm`
- `Base.Wound_Chest_Bite_Male`

必须保留：

- `Base.Bandage`
- `Base.Hammer`
- `Base.NailsBox`
- `Base.Axe`

系统币测试口径：

- 不要把当前 GodSystem 系统币列为“抽奖候选必须保留”。它们是经济货币，不应因为过滤层测试而进入奖池。
- 可以单独验证过滤层不会仅因 `GodSystem.*` 模块名误杀自定义 MOD 物品，但抽奖候选仍应受候选来源、黑名单和管理员开关约束。

功能验证：

- 单人抽奖预览不再显示 `ZedDmg/Test/Dummy`。
- 单人抽奖多次抽取不会发放 `ZedDmg/Test/Dummy`。
- 多人抽奖由服务端过滤，客户端不能通过本地候选池差异抽到隐藏物品。
- 分类抽奖和全种类抽奖都应用同一过滤规则。
- 管理页关闭某物品抽奖后仍生效。
- 管理页启用某隐藏物品不会绕过 `hidden/obsolete` 基础过滤。
- `getScriptManager()`、`FindItem()` 或脚本物品字段 API 不可用/报错时，抽奖候选构建不能失败放行，也不能整池报错。
- 客户端过滤 helper 和服务端过滤 helper 对同一批样本返回一致结果。
- 过滤后某分类为空时，分类列表、预览数量和抽奖按钮状态不会保留旧数量。
- `Base.Bandage` 保留测试必须和 `Base.Bandage_LeftUpperArm` 排除测试成对存在，确认没有因为 `bandage` 字符串匹配误杀真实医疗物品，也没有放过隐藏的 body bandage 服装项。

## 风险

- 如果某个第三方 mod 没有正确设置 `hidden`，仍可能需要后续追加更精准的模式过滤。
- 过宽的名字黑名单会误伤真实 mod 物品，因此第一版不要做全局 `Test` 字符串排除。
- 过宽的 `BodyLocation`/名称匹配会误伤 `Base.Bandage` 或真实 mod 服装，必须只读脚本物品 body location 字段。
- 如果客户端/服务端复制两份过滤 helper，后续维护容易规则漂移；优先 shared，实现镜像时必须有一致性测试。
- 当前方案最低只修抽奖。若不接入商店/管理页/价格表生成，隐藏物品仍可能留在价格表或非抽奖 UI 中，不能对外描述为“经济系统全局已清理”。
- 如果未来要重生成 `GodSystem_Prices.lua`，生成脚本也应接入同一套可用性过滤，否则运行时过滤虽然能挡住问题，价格表仍会继续膨胀。
- 如果把 CAEC 的 `instanceItem` 逻辑引入 GodSystem，需要单独评估性能和异常物品风险，不应作为这次修复的默认方案。

## 二次审核结论

本方案经二次审核后可以作为 v1.16.34 的开发依据，但开发时必须遵守以下修正：

- 过滤层在抽奖上下文中必须失败关闭，不能继承现有 `itemExists()` 的失败放行行为。
- 系统币不作为抽奖候选保留样本；只作为“自定义模块不要被误杀”的独立兼容性样本。
- `BodyLocation` 过滤只能读脚本字段或 `ItemBodyLocation` 枚举，不能用物品名/`fullType` 粗暴匹配；必须同时覆盖真实 `Base.Bandage` 和隐藏 `Base.Bandage_*` 的边界。
- v1.16.34 若只接入抽奖，就按“抽奖奖池修复”发布；不要宣传为全经济系统清理。

## 下一步实施建议

如果用户确认进入开发，建议版本提升到 v1.16.34，按以下顺序做：

1. 备份当前 v1.16.33 稳定版本。
2. 增加 shared 优先的 `isEconomicItemAllowed` 过滤 helper；如必须镜像客户端/服务端实现，先写一致性测试。
3. 添加静态测试脚本覆盖上述必须排除/必须保留物品、失败关闭、管理员开关、系统币测试口径和客户端/服务端一致性。
4. 接入客户端抽奖预览、服务端抽奖发放、旧商店抽奖兼容路径。
5. 检查中文本地化没有新增乱码。
6. 更新 `GodSystem_DevHandoff_CN\07_版本记录.md` 和 Workshop 更新说明。
7. 用户测试稳定后，再替换稳定备份。
