# B42.21 负重优先策略与创意工坊检索

日期：2026-10-10。基线：GodSystem `42.21_3.21.4`。

本次是研究与隔离验证，没有修改运行代码、版本号、部署副本或已验收备份。用户已确认可以优先保证本 MOD 的负重功能，不要求保留其他 MOD 对同一负重字段的调整。

## 2. 同补丁原版事实

本机 `projectzomboid.jar` SHA-256：
`e1a69eb743ede60b213a0fe7f8b83d4fcab773036d256cc4543a336f3b058a33`。

只抽取相关类，在忽略目录 `.test-runtime/carry-b4221-review` 反编译；原版类及源码不进入运行包或 Git。

- `IsoGameCharacter`：`maxWeightBase` 初值 8；`setMaxWeightBase(int)` 只写字段；`getWeightMod()` 根据真实力量等级返回倍率，力量 5 为 1.58、10 为 2.5。
- `BodyDamage.UpdateStrength()`：先截断 `base × strength`，扣除饥饿、口渴、疾病、出血、受伤的惩罚，钳制非负，再乘玩家 `maxWeightDelta` 并截断。
- `IsoPlayer` 创建时根据原版特质初始化 `maxWeightDelta`：Strong 1.5、Weak 0.75、Feeble 0.9、Stout 1.25，否则 1。强制优先不能把这些合法特质效果直接清成 1。
- `BodyDamage.Update()` 在多人客户端活着的玩家分支提前返回，不自动执行其内部的 `UpdateStrength()`。直接从 Lua 调用 `UpdateStrength()` 是另一条可用路径，不能混为一谈。
- `zombie/network/packets/character/PlayerDamagePacket`：发送服务端 `getMaxWeight()`；客户端解析时直接调用 Java `setMaxWeight()`。Lua 方法包装拦不住这次原生内部调用。
- 本地玩家的 `OnPlayerUpdate` 在 `IsoPlayer.updateInternal2` 触发，随后通常执行 `super.update()` 与身体状态更新；服务端远端玩家走不同分支，不能只依赖这个事件。
- `IngameState` 在世界更新后触发 `OnTick`；专服主循环也运行 `IngameState.update()`。同一个事件内的其他 MOD 回调顺序仍不能视为固定最高优先级。
- `ItemContainer.getMaxWeight()` 对角色直接读取 Java 角色负重；实际存放容量和超重阈值是不同问题。原版容器仍有其容量钳制，不因负重阈值提高自动解除。
- `LuaManager.Exposer` 将 `IsoGameCharacter`、`IsoPlayer` 和 `BodyDamage` 加入可见类集合，并进行 `exposeLikeJavaRecursively`；`UpdateStrength()` 是该补丁的公开方法。接口证据不只来自 Lua 表替身；实际世界生命周期及多人收包时序仍需实机确认。
- `NetworkPlayerAI.syncDamage()` 的服务端分支发送原生 `PlayerInjuries` 和 `PlayerDamage`。基础类同名方法为空；不能拿基础类反编译结果认为完全没有同步。也不能把设置负重字段等同于立即发送这些包，或在 Lua 中使用未开放的网络 AI 方法。

## 3. 已复现的 GodSystem 问题

使用现有 `CarryNativeProbe` 编译产物，绑定本机当前游戏 JAR，通过 Kahlua 调用真实负重字段和 `BodyDamage.UpdateStrength()`。测试替身提供角色构造、力量倍率与身体状态，不加载游戏世界，不代表 SP／MP 实测。

### 3.1 基础值覆盖导致恢复与购买被拒绝

三次升级形成基础值 14。将基础值改为 15 后，连续 20 次恢复均返回 `externalConflict`，下一次购买也返回相同结果。这是当前主动保护的行为，不是接口不能写入。

### 3.2 仅最终值覆盖时漏检

在延后核对已经完成后，基础值保持 14，只把最终负重从 22 改为 12。连续 20 次恢复都返回成功，状态为 `ok`，最终值一直保持 12。再次主动安排核对才恢复为 22。

这说明当前稳定检查没有完整核对最终字段。多人原生收包确实会写该字段，但尚不能认定玩家反馈一定由这一条路径触发；服务端与客户端基线不同、其他写入仍需结合日志区分。

## 4. 最高优先级原型验证

忽略目录内的 `priority-behavior.lua` 通过以下检查：

1. Lua 把 `getWeightMod()` 包装为 999；Lua 读取为 999，但 Java 原生重算仍得到 12。证明包装入口不等于修改 Java 公式。
2. Lua 包装 `setMaxWeightBase()`，将通过该入口的写入固定为 14；原生重算得到 22。
3. 使用包装前捕获的原生 setter 仍能写回 8，绕过包装；再核对原生字段能够修复为 14／22。
4. 10,000 次稳定基础字段检查不产生额外纠正写入。只验证该原型的基础字段检查，不代表未来控制器总耗时。
5. 特质倍率 1.5 正常参与计算，结果 33；最终字段被改为 12 后，显式原生重算恢复为 33。

不能把这个隔离原型说成覆盖所有 MOD 或已通过多人同步。

## 5. 参考源码审计结果

### Fix Carry Capacity：固定最终阈值

共享 `CapacityCore.lua` 通过三个原生字段共同实现：基础值取至少 21 或目标阈值加 20；根据力量与身体状态计算乘特质倍率前的值；将倍率补偿为 `(目标阈值 + 0.5) / 该值`，同时写入最终阈值。它没有改写 Java 公式，也没有通过 Lua 包装力量 getter 改变 Java 内部计算。

因此设置 60 后，力量、原版特质和身体惩罚的最终效果会被持续补偿，目标仍为 60。这适合它的固定容量玩法，不符合 GodSystem 在原版机制上增加基础负重的规则。当前负载大于配置时，它还会把阈值临时提高至负载向上取整；GodSystem 不采用这个行为，以免升级能力自动跟着携带物品无限增长。

客户端每次 `OnPlayerUpdate` 应用角色设置，每 60 次更新执行背包递归检查；多人每 600 次本地玩家更新重新请求服务器配置或重发本地配置。服务端每 30 个 tick 应用角色及背包设置，每 300 个 tick 发送权限配置。这些是源码计数，不是固定秒数，不能在不同 FPS／服务器帧率下承诺相同间隔。背包功能关闭时仍遍历以恢复先前管理过的背包。

其角色路径还调用 `getCapacityWeight()`；B42.21 中该接口会进入角色 `getInventoryWeight()`，后者遍历主背包物品。因此不能将参考方案称为“每帧只处理几个字段、完全没有物品遍历”。GodSystem 的优先纠正不需要照搬这次重量读取及背包扫描。

多人未启用强制配置时，参考 MOD 有意允许客户端提交自选容量；不能照搬到付费升级。可借鉴的是服务端一致配置与持续纠正，而不是客户端自报等级／容量。

`InventoryLayout.lua` 只调整容器标题文字的位置，没有给实际负重另加一个隐藏计算机制。

### UCWF：参与式协作

共享框架只运行于 SP／服务端。基础流水线从 8 开始合并登记加成，设置倍率为 1，再通过临时 `OnTick` 工作器延后处理最终倍率；默认沙盒开关将目标限制为 50。框架本身不直接调用 `UpdateStrength()`，依赖游戏在两个阶段之间重新计算。

默认 50 上限与 GodSystem 当前的框架购买校验结合，会出现达到上限后拒绝再购买；它不证明原版负重只能提高到 50。现有适配的正常重算和回滚已通过下节隔离测试，但没有证明任意其他 MOD 及事件顺序下都稳定。

只登记基础加成、没有补回原版特质的最终修饰器时，框架会把原本的倍率 1.5 重置为 1。前置负重为 0 时，最终倍率阶段还可能出现 `0 / 0`。两项均是所下载版本的源码与隔离观察，不能泛化为全部玩家都会遇到；自己的控制器应保留合法特质，并避免使用无保护的反推除法。

它解决愿意登记的 MOD 之间的组合，不保护来自框架外的 setter，也不提供绝对写入优先级。两个 example/test 文件明确提前返回，不能当作默认运行中的额外守护器。

### DUFA：服务端倍率控制

值得借鉴的是服务端按确定性来源构造倍率并定期核对。其百分比／公斤加成最终写入同一个倍率字段；从最终值反推基线存在取整、低倍率与身体状态边界。GodSystem 更适合直接控制基础字段，并让当前补丁的原生计算完成最终值。

## 7. 建议实施方向（未实施）

### 确定性基础值

保持每级 2 基础负重及当前费用规则，用原版基础 8 加账号已购买加成得出目标。不再把不明外部值重新当基线，不反复叠加。已有购买等级保留；同一字段的外部加成不保证保留，符合用户本轮优先级决定。

对享有本功能且已购买等级的角色，取消因外部数值冲突导致的冷却／拒绝购买；真正的接口异常、溢出、余额不足和扣款失败仍保留拒绝及回滚。

### 原版特质与公式

优先保留原版力量、身体状态和特质倍率。若需要屏蔽外部倍率，按原版特质规则确定自己的倍率，而不是从已被改写的实时倍率反推。仍调用原生 `UpdateStrength()`，不把 Java 公式复制为第二份成交或同步依据。

### 写入入口保护与原生字段核对

窄范围包装已购买角色的 Lua 负重写入入口，其他角色及功能关闭状态正常调用原版。覆盖 `IsoPlayer` 与基类的真实方法查找链，防递归，并使用原生测试验证重载与返回值。

入口包装只是第一层。对已激活角色轻量核对实际字段，处理捕获旧 setter、Java 内部写入及延后框架工作器。稳定时不重新读取账号、扫描背包、调用报价或每帧发送网络消息；只在变化时写入。最终值核验要区分正常力量／身体状态变化，不能拿上次最终值强行盖掉新的原版结果。SP／服务端发现最终字段变化时重新执行原生计算，可区分正常变化与外部错误写入，无须复制原版身体惩罚公式。

不要因为目标是“最高优先级”就无条件每帧反写三个字段或重算全体账号。可在现有低频任务管理账号与生命周期，另为已激活角色维护有限的字段核对；实际采用的节流与事件时机应由原型统计决定。若包装不能可靠安装，仍可用字段纠正实现恢复，不把入口包装当成可订阅纯 Lua 方案成立的唯一前提。

不能宣称 Lua 全局“永远最高优先级”：其他 MOD 可替换同一入口、缓存原生函数、使用 Java 组件或在更晚时机写入。目标是普通 Lua 写入受控、原生旁路及时恢复，明确剩余边界。

### SP／MP 权威

SP 在本地维护；MP 必须由服务器根据账号等级计算，并通过现有状态投影传递一致的目标基础及倍率。客户端不各自猜测外部基线，不接受客户端自报等级，也不与服务器最终值持续争写。当前普通模式只投影等级、在两端自行接受不同外部基线，不适合继续作为强制优先的协议。

最终值同步另行明确：原生伤害包会携带最终负重，但不能假设每次 setter 都触发发送。升级／恢复后的权威结果可经现有 CarryState 投影；字段改变才递增版本，并验证其与原生包交错到达的行为。MP 客户端不得以过期缓存覆盖服务器新身体状态产生的正常负重，也不应持续执行本地 `UpdateStrength()` 与原生收包争写。

现有 UCWF 自动适配应与强制优先策略统一设计：不能一边让框架重新计算、另一边在同一帧持续反写。按用户已经确认的优先目标，建议已购买角色不再自动交由 UCWF 汇总，退出自己的修饰器时使用零贡献／注销自己记录的方式，不删除其他 MOD 的登记表或全局监听。零级、关闭功能及不参与本功能的角色正常保留其他 MOD 行为；不要求新增框架依赖。

### 后续验证

- 当前两条复现作为回归；每级收益、力量与原版四种特质、饥饿／受伤状态、零级及功能关闭。
- 外部基础／倍率／最终值写入、缓存原生 setter、延后回调、重生重连、账号等级恢复，不累计放大。
- 购买扣款失败回滚、旧等级与存档保持、超过数值边界拒绝。
- MP 服务器原生重算和 `PlayerDamagePacket` 到达后的客户端实际值一致；房主／专服需实机确认。
- 统计稳定字段读取、实际写入、纠正耗时和网络消息，不以“没有背包扫描”代替性能测量。
- 原版容器存放上限与角色负重阈值分别测试，避免仅显示增加的误判。

本研究完成参考源码审计和上述隔离验证。建议下一版采用“确定性原版基础＋账号升级、原版特质倍率、主动字段纠正、服务端一致投影”，修正现有冲突拒购与最终值漏检；不采用固定最终负重或跟随负载增长规则。本轮仍未修改正式功能、版本、部署、备份或提交 Git。
