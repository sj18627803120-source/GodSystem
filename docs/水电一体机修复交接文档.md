## 已复现的故障

2026-09-23 单人游戏日志 `C:\Users\wan20\Zomboid\console.txt` 显示 `GodSystem_UtilityGenerator.lua:503: '<eof>' expected near 'end'`。共享模块加载失败后，客户端 `GodSystem_UtilityGeneratorContext.lua:450` 的 OnTick 和 `:361` 的右键菜单回调持续索引空模块，导致进入游戏即报错、专用右键菜单消失。已经激活的原生发电机仍可能保留燃料并供电，因此“仍在供电”不能证明 Lua 水电模块正在运行。

## 本次处理

- 删除误加入 `refillGeneratorWater` 的多余 `end` 和无条件免费灌水分支，修复 Lua 5.1 语法；客户端定时和菜单入口在模块缺失时安全返回。

- 接水只选背包中具有原生 `FluidContainer` 且为空或已有清水的物品，客户端传物品 ID，服务端重新定位并实际注水。饮水在权威端使用原版 `FluidContainer` 与 `DrinkFluid`；客户端不再直接改 `UsedDelta` 或口渴值。
- 设备水箱预存水按真实取用扣减预留费用，未用部分停机或搬走时退款；修正了此前“取水时把费用退回余额”的漏洞。水箱补给限每 60 秒检查，不再每秒对所有设备额外遍历一次。
- 目标原生燃料读数不可用时发电机保持关闭，避免零费用激活。自动预存燃料上限设为 10 原版燃料单位，避免一次充值全被电力预存占用而无法供水；充值后立即尝试补给。停止或功能关闭时清理未使用的水箱预留。
- 中文乱码不能仅凭 CRLF 行尾推断原因；本次从 UTF-8 YAML 源重新生成 CN／CH／EN、Lua fallback 和相关文本，静态校验检查 U+FFFD。

## 后续供水实测反馈与本地修复

用户确认供电正常，设备直接饮水/接水可用，但固定水龙头无水，且直接接水每次仅 1 L。对照本地 B42.20.4 原版 Lua 与已下载的 OrangeCommunityEconomy 参考 MOD 后，发现两个代码层面的阻断点：`GodSystem_B42JavaCalls` 没有注册 `PropertyContainer:has`，真实 Java 对象的 `waterPiped` 检查始终失败；原供水逻辑只接受具有原生流体容量的对象，而固定水龙头可能没有 `FluidContainer`，参考 MOD 对此使用游戏识别的 `modData.waterAmount` / `waterMaxAmount` 储水字段。原版 `CustomTileProps.lua` 也存在这些字段；是否对玩家当前设施生效，仍须 B42.20.4 实机回读验证。

本轮本地源码已补 Java `has` 桥、两类设施供水路径及写后回读；固定水龙头缓冲上限 100 L，按实际注入量预留费用，停止/搬走时先移除未用水，成功后才退款。仅用已核验的 OrangeCommunityEconomy 控制标记判定他 MOD 占用，避免把原版或未知字段误判为冲突。未接通管道的移动设施不接管。直接接水取消 1 L 单次上限，按容器剩余容量与设备最多 50 L 水箱余额供给。设备维护表每秒最多处理一次；供电 30 秒、水扫描 60 秒，扫描工作器保持每帧最多 96 格和约 2 ms 预算。

针对固定水龙头储水、原生流体、第三方已占用、停机移除失败不退款、完整容器接水和每秒维护限频加入 Lua 5.1/Kahlua 回归。Lua 5.1 全包编译与行为测试、B42.20.4 Kahlua、`Test-GodSystem.ps1` 均通过。已重新镜像到 Workshop 测试副本，571 个非开发文件逐文件 SHA-256 完全一致，部署目录静态检查通过。自动化尚不能证明玩家实机水龙头菜单、Java 内部储水回读、多人同步与存档恢复；仍待 SP、房主和专用服复测。

## 水电账户拆分

用户明确选择水、电分别充值和扣费，旧共享余额全部转入水账户。设备记录首次读取时以常数开销完成惰性迁移，迁移后移除旧余额字段，重复读取不重复增加；既有水量、燃料和预付费用仍保留。新菜单在“充值账户”下分“水账户”“电账户”，各有 100/500/1000 币选项；状态分别显示可用余额与预存费用，再显示供水、供电结果。服务端仅从对应账户预扣，未用预留只退回该账户；两账户均随设备 ID 移动。新充值操作的指纹包含账户类型，旧未带账户字段的请求仍保留原指纹格式并默认进入水账户，保证已有未结束操作不被误判为不同请求。

启动状态同时尝试水和电两项服务；各账户余额不足时只影响该项服务。停机同时关闭发电机、设备接水与附近设施补水，并用原有分帧清理工作器移除设施内未用的预付水。检查中另发现 SP/服务端入口此前每秒才调用一次分帧工作器，较大范围可能需约两分钟才能扫完；现在仅在有扫描/清理任务时逐帧推进，每帧仍限制最多 96 格和约 2 ms，无任务时继续每秒检查一次。清理失败时同一设施至少间隔 1 秒重试。新账户结构和真实世界对象同步还需实机复测，自动测试不能代替这一项。

最终自动检查：Lua 5.1 全包编译 135 文件、行为回归、B42.20.4 Kahlua 及静态包检查均通过。设备关闭时直接建立清理任务；已预付到附近水设施的水按分帧预算移除，停止后的极短清理期间不应再补水。最终测试副本部署记录和哈希核对见交接 112，游戏内原生水龙头是否回读成功仍待实测。
